# ADR-020 — Dashboard web da Juniper (somente leitura, na tailnet)

- **Status:** Aceito (projeto aprovado em 2026-10-25; implementação na épica #159, tasks T-130 a T-137)
- **Data:** 2026-10-25
- **Autor:** Equipe Juniper
- **Contexto do Sprint:** Memória V2, observabilidade da memória
- **Relaciona-se com:** [ADR-007](ADR-007.md) (token), [ADR-012](ADR-012.md) (protocolo), [ADR-013](ADR-013.md) (produção e Tailscale), [ADR-017](ADR-017.md) (Memória V2), [ADR-018](ADR-018.md) e [ADR-019](ADR-019.md)

---

## Contexto

Os dados da memória (fatos, lembranças refinadas, sentimentos, estudos e notas, personalidade, sonhos) só podiam ser vistos por comandos no terminal. O usuário quer **ver** essas informações num dashboard visual, responsivo, acessível de qualquer dispositivo da tailnet, com pesquisa.

## Decisão

1. **Uma superfície nova do cérebro, não um cliente com acesso ao banco.** O dashboard é o módulo `brain/dashboard/`, que roda **dentro do processo do servidor** (`juniper serve`) e usa o código de memória do próprio cérebro. O navegador nunca fala com o MongoDB (regra 2 do CLAUDE.md). `brain/core` não conhece o dashboard.
2. **Somente leitura.** Nenhum endpoint escreve no banco. Só `GET` é respondido (qualquer outro método é 405). Ações como esquecer uma memória continuam nos comandos de terminal; entrariam depois, com confirmação, e exigiriam revisar este ADR.
3. **Porta 8766, só na tailnet.** O compose de produção publica `${TAILSCALE_IP}:8766`, como faz com a `8765`; nunca em `0.0.0.0` (ADR-013). A ACL do Tailscale precisa liberar essa porta para os dispositivos do usuário. HTTP puro basta (o tráfego da tailnet já é criptografado); HTTPS por `tailscale serve` é opcional e não exige código.
4. **Autenticação: o token do ADR-007.** A tela de login manda o token num cabeçalho `Authorization` (nunca na URL) e recebe um cookie `HttpOnly; SameSite=Strict`, assinado por HMAC derivado do token e com prazo (`dashboard.session_hours`, 12). Trocar o token derruba as sessões. Falhas de login são limitadas por cliente (5 em 5 minutos). A rede privada e o token continuam sendo duas travas independentes.
5. **Defesas do navegador:** o cabeçalho `Host` precisa ser um IP, `localhost`, um nome `*.ts.net` ou um host configurado (contra DNS rebinding); CSP restritiva (nada inline, nada externo), `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, sem CORS; respostas da API sem cache.
6. **Servidor HTTP sem dependência nova:** usa a `websockets` que o cérebro já tem, respondendo tudo em `process_request`.
7. **Isolamento:** o dashboard sobe junto do servidor, mas uma falha dele (porta ocupada, erro numa rota) é registrada e engolida: nunca derruba o servidor nem a conversa. Pode ser desligado (`dashboard.enabled: false`).
8. **Privacidade:** segredos mascarados em tudo que sai; vetores nunca saem; as conversas (transcrições) aparecem só com `dashboard.transcripts: true` (padrão), com segredos mascarados.
9. **Frontend sem etapa de build:** HTML, CSS e JavaScript simples, bibliotecas de gráficos empacotadas no repositório (sem CDN, sem fontes remotas).

## Consequências

- Uma porta nova na superfície de ataque, restrita à tailnet e protegida por token. Mitigação: somente leitura, limite de tentativas, `Host` validado, CSP.
- O dashboard divide o processo (e a memória RAM) do servidor. Em troca, reaproveita o modelo de embeddings já carregado para a pesquisa por significado.
- Mudou a regra do ACL: a política do Tailscale precisa permitir a `8766`.

## Alternativas descartadas

- **Contêiner separado lendo o Mongo:** isolaria falhas, mas carregaria o modelo de embeddings uma segunda vez e daria a um serviço novo acesso direto ao banco.
- **Dashboard com escrita desde o início:** aumenta o risco (confirmação, CSRF, auditoria) sem ser o que foi pedido agora.
