# ADR-011 — Arquitetura de Memória

- **Status:** Proposto (itens marcados **[a confirmar]** aguardam decisão do Petrus; o merge deste ADR é a aprovação)
- **Data:** 2026-10-13
- **Autor:** Petrus Rennan
- **Contexto do Sprint:** Sprint 2 — "Memória" (O Hipocampo)
- **Relaciona-se com:** ADR-003 (config), ADR-006 (segurança), ADR-007 (deployment), T-050 a T-060

---

## Contexto

Hoje a Juniper só lembra do que está na conversa aberta, e `Session` guarda no máximo 8 turnos em RAM. Fechou o terminal, esqueceu tudo. O marco da Sprint 2 é outro: lembrar que o Petrus prefere ZSH, que odeia tabulação com espaço e que o projeto X usa Laravel 11, e usar isso sem que ele repita.

Isso mistura dois problemas diferentes, com ciclos de vida diferentes:

1. **Conversa atual** (curto prazo): o que foi dito há pouco, em ordem, inteiro.
2. **O que importa** (longo prazo): fatos duráveis, destilados de várias conversas, achados por **significado** e não por palavra ("PHP framework" tem que achar "Laravel").

Também pesam as decisões anteriores: o brain vai rodar numa VPS sem GPU (ADR-007), com MongoDB como banco; a sprint roda **local** (`deployment.mode: local`) e o deploy vem na Sprint 3.

Analogia: a memória de sessão é a mesa de trabalho (tudo à mão, mas limpa no fim do dia); a de longo prazo é o caderno de anotações (curto, organizado, consultado quando o assunto aparece).

---

## Decisão

### 1. Duas camadas

| | Sessão (curto prazo) | Longo prazo |
|---|---|---|
| O que guarda | Mensagens da conversa, incluindo tool calls | Fatos duráveis em texto curto |
| Granularidade | Turnos completos, em ordem | Uma memória = uma afirmação |
| Como é achada | Vai inteira para o LLM, dentro de um orçamento de tokens | Busca por similaridade (RAG) |
| Duração | Uma conversa, retomável | Até ser apagada |
| Módulo | `brain/core/session.py`, `brain/memory/session.py` | `brain/memory/` (vetorial, embeddings, store) |
| Task | T-051 | T-053 a T-058 |

### 2. Memória de sessão

- **Identidade:** cada `Session` tem `id` (ordenável por data), `created_at` e `updated_at`.
- **Orçamento de tokens:** além do teto de turnos (`memory.session.max_turns`), a sessão respeita `memory.session.max_tokens`. Tokens são **estimados** (≈ 4 caracteres por token), sem dependência de tokenizer. Estourou, descartam-se os **turnos mais antigos, inteiros** (uma mensagem do usuário e tudo que veio depois dela, tool calls incluídas), para nunca deixar uma resposta de tool órfã. O turno atual nunca é descartado.
- **Sem resumo por LLM no MVP.** Resumir mensagens antigas custa uma chamada extra a cada estouro. O que for descartado da sessão que valha ser lembrado vira memória de longo prazo (T-056), que é o papel dela. Resumo fica como evolução.
- **O prompt de sistema não é persistido**, só o histórico. Ao retomar, vale a persona atual.
- **Persistência atrás de uma interface** `SessionStore` (`save`, `load`, `latest`, `list_sessions`). A primeira implementação grava **um arquivo JSON por sessão** em `~/.juniper/sessions/` (diretório `700`, arquivos `600`, escrita atômica), porque o MongoDB só chega na T-053. A implementação em MongoDB entra com a T-053 e passa a ser a usada quando houver servidor (Sprint 3); o resto do código não muda. **[a confirmar]**
- **Retomada:** `juniper --resume` retoma a conversa mais recente. Confirmações pendentes (`Dispatcher.pending`) **não** sobrevivem ao reinício: depois de retomar, nada é executado sem nova confirmação (ADR-006).
- **Falha de disco não derruba a conversa:** erro ao salvar vai para o log e a conversa segue.

### 3. Memória de longo prazo

**Tipos** (campo `type`):

| Tipo | Guarda | Exemplo |
|---|---|---|
| `preference` | Como o usuário gosta de trabalhar | "Prefere ZSH." "Odeia tabulação com espaço." |
| `project` | Fatos sobre os projetos dele | "O projeto X usa Laravel 11." |
| `fact` | Outros fatos duráveis sobre ele ou o mundo dele | "Mora em São Paulo." |

**Vale guardar** o que (a) continuará verdadeiro por semanas e (b) mudaria uma resposta futura. **Não vale:** conversa social, pedidos pontuais ("marca dentista amanhã", isso é da agenda), conteúdo lido da web, saídas de comandos, e **qualquer segredo** (ver seção 6).

**Documento** (coleção `memories`):

```json
{
  "_id": "mem_01JAB3...",
  "text": "O projeto X usa Laravel 11.",
  "type": "project",
  "status": "active",
  "superseded_by": null,
  "embedding": [0.012, -0.087, 0.231],
  "embedding_model": "intfloat/multilingual-e5-small",
  "source": { "kind": "extracted", "session_id": "20261013-221500-a1b2c3" },
  "created_at": "2026-10-13T22:15:00Z",
  "updated_at": "2026-10-13T22:15:00Z"
}
```

(`embedding` abreviado; no banco tem a dimensão inteira do modelo, 384 no `multilingual-e5-small`.)

| Campo | Significado |
|---|---|
| `status` | `active` (usada na busca) ou `superseded` (substituída; fica só para auditoria) |
| `superseded_by` | id da memória que a substituiu |
| `embedding_model` | modelo que gerou o vetor. Vetores de modelos diferentes **não** são comparáveis: trocar de modelo exige reindexar tudo (comando previsto na T-054) |
| `source.kind` | `extracted` (a Juniper tirou da conversa, T-056) ou `explicit` (o usuário mandou lembrar, T-058) |

**Índices:** `(status, type)` e `created_at`. O vetor **não** tem índice no MVP (ver seção 5).

### 4. Atualização e contradição

Memória nunca é editada no lugar. Quando entra uma informação que **contradiz** uma ativa ("migrei o X para o Laravel 12"), a nova nasce `active` e a antiga vira `superseded` com `superseded_by` apontando para ela. A busca só enxerga `active`.

Informação **equivalente** a uma ativa não cria duplicata (só atualiza `updated_at`). Quem decide "equivalente", "contradiz" ou "novo" é a etapa de extração (T-056), comparando a candidata com as memórias mais próximas.

`forget` é **exclusão de verdade** (some do banco), a pedido do usuário. `superseded` é para auditar atualizações, não para guardar o que ele mandou esquecer.

### 5. Interfaces (trocáveis)

Decisões já tomadas, cada uma atrás de uma interface para trocar depois sem mexer no resto:

| Interface | Primeira implementação | Troca futura |
|---|---|---|
| `EmbeddingProvider` (`embed`, `embed_batch`, `dimension`, `model_id`) | Modelo multilíngue **local em CPU** (`multilingual-e5-small`, ONNX), carregado sob demanda | API externa |
| `VectorStore` (`add`, `search(vector, top_k, threshold, filters)`, `update`, `delete`) | Carrega vetores do MongoDB e calcula **cosseno em Python** (numpy) | **Atlas Vector Search** (`$vectorSearch`) |
| `SessionStore` | Arquivos JSON | MongoDB |

Por que local e cosseno: o volume é pessoal (centenas a poucos milhares de memórias), o cosseno responde em milissegundos nessa escala, não exige Atlas, e o texto das memórias não sai da máquina para gerar embedding. A migração só é necessária se o volume chegar a centenas de milhares.

### 6. Privacidade e segurança

- **Segredos nunca entram.** Antes de gravar (extração ou `remember`), o texto passa por um filtro que recusa o que parece chave de API, token, senha, número de cartão e chave privada. Em dúvida, recusa. **[a confirmar]**
- **Memória é dado, não instrução.** Ao injetar no prompt (T-057), as memórias vão num bloco delimitado e rotulado como "fatos conhecidos sobre o usuário"; texto de memória que pareça uma ordem não é obedecido. Isso limita o estrago se algo plantado pela web chegar a ser memorizado.
- **O usuário audita e apaga:** listar, buscar, esquecer e exportar (T-058). A exportação **não** inclui os vetores, salvo pedido.
- **Dados ficam na infraestrutura do próprio usuário** (máquina local ou a VPS dele). Aviso honesto: a **extração** usa o LLM do chat (DeepInfra/Groq/Ollama), então o trecho da conversa analisado vai ao provider ativo, como já vai a própria conversa. Só o *embedding* é local.
- **Sessões em disco** contêm a conversa inteira: ficam em diretório `700`, arquivos `600`. Não há expiração automática no MVP **[a confirmar]**.

### 7. Recuperação (RAG)

A cada mensagem do usuário, busca-se por similaridade entre as memórias `active` e injeta-se o que passar de `memory.retrieval.threshold`, no máximo `top_k`, dentro de `memory.retrieval.max_tokens`. Os valores padrão (`top_k`, `threshold`) são **calibrados na T-055/T-057** com exemplos reais; este ADR não os fixa.

### 8. Configuração (ADR-003)

Nova seção `memory` em `config.yaml`, cada task acrescenta a sua:

```yaml
memory:
  session:                    # T-051
    max_turns: 8
    max_tokens: 6000
    dir: ~/.juniper/sessions
  mongo:                      # T-053
    uri: mongodb://localhost:27017   # credenciais só no .env
    database: juniper
  embeddings:                 # T-054
    model: intfloat/multilingual-e5-small
  retrieval:                  # T-055 / T-057
    top_k: 5
    threshold: 0.0            # calibrar
    max_tokens: 500
```

## Consequências

- A conversa passa a sobreviver ao terminal (`--resume`), já na T-051, sem esperar o MongoDB.
- Trocar o modelo de embeddings exige reindexar (o campo `embedding_model` permite detectar isso).
- Memória substituída fica no banco, marcada, enquanto o usuário não mandar esquecer; é um custo pequeno de armazenamento pelo ganho de auditoria.
- A qualidade da memória depende do LLM de extração: ele pode lembrar o que não devia ou deixar de lembrar. Por isso `juniper memory list/forget` (T-058) é parte do escopo, não um extra.
- O filtro de segredos é heurístico; não garante 100%. Quem cola uma senha na conversa ainda a deixa no arquivo de sessão (ver seção 6).
- Não validado neste ADR: latência real do modelo de embeddings na VPS e a qualidade da busca em PT-BR. Ambos são medidos na T-054/T-055 (e documentados nos PRs).
