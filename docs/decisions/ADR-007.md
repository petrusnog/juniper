# ADR-007 — Arquitetura de Deployment

- **Status:** Aprovado
- **Data:** 2026-10-01
- **Autor:** Petrus Rennan
- **Contexto do Sprint:** Pré-Sprint 1 (destrava T-010)
- **Relaciona-se com:** T-003, T-004, T-010, T-012, T-015, Sprint 2+

---

## Contexto

A Juniper v4 foi desenhada como agente autônomo com tool calling, memória de longo prazo e (futuramente) voz. A visão declarada do projeto é inspirada no J.A.R.V.I.S. do Tony Stark: **sempre disponível, acessível de qualquer dispositivo, com memória persistente e capacidade de agir no mundo real**.

A decisão inicial de "PC como servidor" foi rejeitada pelo usuário por inviabilidade prática: manter um PC ligado 24h apenas para servir a Juniper é custoso em energia, desgasta hardware e amarra o acesso a estar em casa.

Precisamos definir **onde o cérebro roda**, **como os clientes o alcançam** e **como tools que agem em dispositivos específicos são executadas**.

---

## Decisão

Adotamos uma arquitetura **cliente-servidor distribuída com brain em nuvem e executores locais efêmeros**.

### Visão geral

```text
┌──────────────────────────────────────────────────────────┐
│  VPS (o cérebro — sempre online)                         │
│  • Agent loop, LLM router, memória                       │
│  • Tools "cloud": web_fetch, calendar, email             │
│  • Sem GPU, sem LLM local — usa APIs (Groq primário)     │
└────────────────────┬─────────────────────────────────────┘
                     │ WebSocket persistente + HTTPS
      ┌─────────────┼─────────────┬──────────────┐
      ▼             ▼             ▼              ▼
 ┌─────────┐   ┌─────────┐   ┌──────────┐   ┌──────────┐
 │   PC    │   │ Celular │   │Raspberry │   │ (futuro) │
 │ (quando │   │ (sempre │   │  (casa)  │   │          │
 │ ligado) │   │ ligado) │   │          │   │          │
 └─────────┘   └─────────┘   └──────────┘   └──────────┘
  executa:      executa:      executa:
  - apps        - notifs      - luzes
  - shell       - apps móv    - som
  - arquivos    - GPS         - sensores
```

**Princípio central:** o cérebro é **único e sempre vivo** (VPS). Os "corpos" (executores) são **múltiplos e efêmeros** — existem enquanto o dispositivo está ligado e desaparecem quando desligam.

---

### Componentes

#### 1. Brain (VPS)

- Roda o `brain/core/` como serviço persistente (`juniper serve`).
- Não executa LLM localmente — a VPS não tem GPU. O LLM é acessado via API (Groq primário, fallback em qualquer endpoint OpenAI-compatible).
- Mantém:
  - Agent loop e dispatcher
  - Roteador de providers (`brain/llm/router.py`)
  - Memória (MongoDB + vetorial)
  - Registro de tools locais (cloud) e catálogo de tools remotas anunciadas por executores conectados
- Expõe API via `brain/clients/server.py` (HTTPS + WebSocket).

#### 2. Clientes (HMI)

Clientes são **finos**: só capturam input (texto/voz) e exibem output. Nunca executam lógica de agente. Nunca acessam o MongoDB diretamente.

- **CLI local** (`brain/clients/cli.py`): terminal do usuário. No Sprint 1, roda em modo `deployment.mode = local` (brain embutido). No Sprint 2+, pode rodar em modo remoto, conectando-se à VPS.
- **PWA / web app**: acesso via navegador do celular. Sprint 2+.
- **Cliente de voz** (celular): STT/TTS nativo. Sprint 4+.

#### 3. Executores (corpos)

Executores são processos leves que rodam nos dispositivos e expõem **capacidades locais** como tools remotas para o brain.

- **PC:** `open_app`, `run_shell`, acesso a arquivos, notificações desktop.
- **Celular:** notificações push, abertura de apps móveis, GPS, câmera.
- **Raspberry/IoT:** Home Assistant, sensores, atuadores.

Cada executor se conecta à VPS via WebSocket e anuncia seu catálogo de tools. Quando desconecta, essas tools desaparecem do brain (com aviso ao usuário quando ele tenta usá-las).

---

### Deployment modes

O `config.yaml` ganha um bloco `deployment`:

```yaml
deployment:
  # local — brain embutido no processo do cliente (Sprint 1)
  # cloud — brain rodando em VPS, clientes remotos (Sprint 2+)
  mode: local

  server:
    host: 127.0.0.1
    port: 8765

  auth:
    # Token estático gerado no primeiro boot (Sprint 2)
    token_file: ~/.juniper/token
```

- **Sprint 1:** `mode: local`. O brain roda embutido no CLI. Nada de rede.
- **Sprint 2+:** `mode: cloud`. O brain roda na VPS; clientes conectam.

---

### Autenticação e exposição

- **Modelo:** single-user, token estático.
- **Geração:** no primeiro boot em modo `cloud`, o brain gera um token aleatório e o salva em `~/.juniper/token` (permissão 600).
- **Uso:** clientes enviam o token em `Authorization: Bearer <token>`.
- **Exposição à rede:** via Tailscale (recomendado) ou WireGuard. A VPS **não expõe portas públicas** para a internet aberta. O Tailscale resolve NAT traversal, autenticação entre dispositivos e encriptação sem configuração extra.
- **Sem multi-usuário.** Sem OAuth, sem cadastro, sem rate limiting por usuário. É um J.A.R.V.I.S. pessoal.

---

### Protocolo brain ↔ executores

- **Transporte:** WebSocket persistente.
- **Mensagens:** JSON-RPC simplificado.
- **Handshake:** o executor envia `register` com `device_id`, `device_name` e a lista de tools disponíveis (nome, schema, tier). O brain registra e responde com `registered`.
- **Tool calls:** o brain envia `invoke` com `tool_name`, `arguments` e `correlation_id`. O executor responde com `result` (mesmo `correlation_id`).
- **Heartbeat:** a cada 30s. Sem heartbeat por 90s → executor marcado como offline e suas tools saem do catálogo ativo.
- **Segurança:** o brain **não pode escalar tier**. Um executor só executa tools com os tiers que declarou no registro. Confirmações (ADR-006) são feitas no cliente que originou o pedido, não no executor.

---

### Política de degradação

O J.A.R.V.I.S. da ficção nunca "não está disponível" — mas a realidade é diferente. A Juniper precisa lidar com degradação de forma graciosa:

| Cenário | Comportamento |
|---|---|
| VPS offline | Clientes exibem "Juniper indisponível no momento" |
| Groq offline | Failover para Ollama (se configurado) ou API alternativa |
| LLM indisponível | Cliente informa que não consegue pensar agora |
| Executor do PC offline | Tools locais do PC ausentes; brain avisa quando solicitadas |
| MongoDB offline | Brain opera em modo "sessão apenas" (sem memória longa) |
| Tailscale offline | Clientes não alcançam a VPS; nada funciona |

## Consequências

### Positivas

- **Sempre disponível** — característica central do J.A.R.V.I.S. preservada.
- **Acessível de qualquer dispositivo** — o cliente é fino, roda em qualquer lugar.
- **Memória centralizada** — uma só fonte de verdade (MongoDB na VPS).
- **Custo previsível** — VPS pequena (~$5/mês) + Groq free tier.
- **Sem dependência de hardware do usuário** — a VPS não precisa de GPU.
- **Corpos múltiplos** — o mesmo brain controla PC, celular, casa, carro, conforme executores forem sendo escritos.

### Negativas

- **Custo mensal recorrente** — diferente de rodar tudo localmente.
- **Dependência de internet** — sem rede, sem Juniper. Offline não é suportado no Sprint 2 (revisar depois).
- **Latência adicional** — cliente → VPS → LLM → VPS → cliente adiciona round-trips. Mitigado por streaming (Sprint 2) e Groq (latência baixa).
- **Superfície de segurança** — mesmo com Tailscale, a VPS é um alvo. Mitigado por: token estático, sem portas públicas, atualizações regulares.
- **Complexidade de implementação** — mais partes móveis (brain, clientes, executores) do que um monólito local. Compensado pela separação `brain/core/` ↔ `brain/clients/` já estabelecida em T-004.

---

## Alternativas consideradas

1. **PC local como servidor (24h ligado).** Rejeitada pelo usuário: inviável em energia e hardware.
2. **LLM local no celular.** Rejeitada: fragmenta a memória, limita a qualidade do modelo (2-4B vs 70B) e consome bateria. Não é a Juniper que estamos construindo, é outra coisa.
3. **Serverless (Lambda, Cloud Functions).** Rejeitada: o cold start mata a sensação de "sempre disponível", e o modelo de agente com sessão persistente não encaixa bem em serverless.
4. **Serviço gerenciado (Supabase, Firebase).** Rejeitada: a Juniper precisa de controle total sobre o processo do agente (tools, subprocess, memória). Serviços gerenciados limitam isso.
5. **Híbrido PC + VPS com sync.** Adiado. Complexidade alta para pouco benefício imediato. Revisar se a latência se provar um problema.
