# ADR-027 — Usuários e credenciais (client_id e client_secret)

- **Status:** Proposto (o merge deste ADR é a aprovação)
- **Data:** 2026-10-30
- **Autor:** Equipe Juniper
- **Contexto do Sprint:** Dashboard V2
- **Relaciona-se com:** [ADR-007](ADR-007.md) (token estático), [ADR-012](ADR-012.md) (protocolo), [ADR-016](ADR-016.md) (Telegram), [ADR-020](ADR-020.md) (dashboard), [ADR-021](ADR-021.md) (login com MFA)

---

## Contexto

Hoje um único token estático (ADR-007) autentica o WebSocket, a CLI remota, o app e o dashboard. Não há noção de usuário nem de dispositivo: quem tem o token é "o dono". O ADR-021 desenhou o MFA em cima disso e **descartou multiusuário** (§8) e sessões no MongoDB.

O próximo passo do produto é ter uma segunda pessoa como beta tester. Isso ainda **não** pede isolamento de dados por usuário, mas pede que a base exista: quem é o usuário, como ele prova quem é e como o dono cadastra e revoga acessos, pela CLI e pelo dashboard.

## Decisão

1. **O usuário é uma entidade.** Campos: `user_id` (UUID), `name`, `role` (`owner` ou `tester`), `status` (`active` ou `disabled`), `created_at`. Existe sempre um `owner`. Só ele cadastra, desativa e revoga.
2. **Credencial = `client_id` + `client_secret`.** Cada usuário tem uma ou mais credenciais (uma por dispositivo ou cliente, cada uma com `label`, `created_at`, `last_used_at`, `revoked_at`). Isso dá, sem tabela extra, a gestão de dispositivos conectados.
   - `client_id`: público, `jc_` + 16 caracteres aleatórios.
   - `client_secret`: `jsk_` + 32 bytes aleatórios em base64url (o prefixo permite ao mascaramento de logs reconhecê-lo).
3. **O segredo é mostrado uma única vez.** No cadastro (CLI ou dashboard) e em cada rotação, a resposta traz o segredo; depois ele **não existe mais em lugar nenhum**, nem para o dono. Perdeu? Rotaciona: gera um novo e invalida o antigo e as sessões dele.
4. **Só o hash é guardado, e é irreversível.** `HMAC-SHA256(pepper, client_secret)`, com o *pepper* num arquivo do servidor (`~/.juniper/auth/pepper`, modo 600, fora do banco, do git e do backup do banco). Um vazamento só do MongoDB não permite nem testar palpites. O segredo tem 256 bits de entropia aleatória, por isso um hash rápido basta (scrypt/argon2 protegem senhas que gente escolhe, não segredos sorteados). Comparação em **tempo constante**.
5. **Armazenamento: MongoDB, com fallback do dono.** Coleções `users` e `credentials`. Se o banco estiver fora, entra só o **dono**, por um espelho local do hash da credencial dele (`~/.juniper/auth/owner.json`, modo 600), atualizado a cada cadastro ou rotação do dono. Os demais usuários ficam indisponíveis até o banco voltar. Isso substitui o §4 do ADR-021 ("tudo em arquivos") para identidade; as sessões de TOTP continuam como o ADR-021 definiu.
6. **Valem para todos os clientes** (CLI remota, app, dashboard, Telegram), exceto o acesso à VPS (SSH), protegido pelo firewall e pelo Tailscale (ADR-013):

   | Cliente | Como apresenta a credencial |
   |---|---|
   | WebSocket (CLI remota, app) | `Authorization: Bearer <client_id>.<client_secret>` no handshake HTTP, como o token de hoje; o `welcome` ganha `user: {id, name, role}` (campo novo, compatível, **sem mudar `protocol_version`**). |
   | Dashboard | A tela de login pede os dois campos; o cabeçalho de `GET /api/login` leva a credencial (nunca na URL); o cookie `HttpOnly; SameSite=Strict` passa a ser ligado ao `user_id` e à credencial, com as defesas atuais. |
   | Telegram | A lista de IDs continua como filtro prévio (ADR-016). Sem sessão, `/login <client_id> <client_secret>` abre a sessão do chat; o bot **apaga a mensagem** com o segredo. |

7. **Migração sem trancar o dono.** O token estático vira uma credencial legada do dono enquanto `auth.legacy_token: true` (padrão na primeira versão). O dono roda `juniper users add` (ou `juniper users bootstrap` no primeiro uso), anota o segredo, atualiza cada cliente e só então põe `auth.legacy_token: false`. Com a chave desligada, o token estático deixa de valer em todos os clientes.
8. **Falhas.** Mesmo erro e mesmo tempo para `client_id` desconhecido, segredo errado, credencial revogada ou usuário desativado (sem revelar qual). Limite de 5 tentativas erradas em 5 minutos por cliente **e** por `client_id`, com bloqueio progressivo. Falha é resultado tipado (`401`/`auth_failed`), nunca derruba o servidor.
9. **Dado com dono, sem isolamento.** Todo registro **novo** (por exemplo, ocorrências) grava `owner_id` com o `user_id` de quem o criou. Registro antigo sem o campo vale como do dono. **Não há filtro por usuário nas leituras ainda**: isolar memória, persona, agenda e música por usuário é uma épica à parte, que exigirá outro ADR. Por isso criar um `tester` fica atrás de `auth.users.allow_testers` (padrão `false`), e a tela e a CLI avisam que ele enxerga o mesmo cérebro.
10. **Primeira rota de escrita do dashboard.** Substitui o §2 do ADR-020 **apenas** para usuários e credenciais: `POST`/`DELETE` só para o `owner`, com token anti-CSRF por sessão, confirmação explícita na tela (digitar o nome do usuário para desativar ou rotacionar) e auditoria. As ações sobre a memória exigirão outro ADR.
11. **CLI.** `juniper users add|list|disable|enable`, `juniper users credentials add|list|rotate|revoke`. Só roda onde há acesso ao servidor (dentro do contêiner na VPS) e o segredo sai no terminal, uma vez. Pedir ao LLM para cadastrar usuário não existe: nenhuma tool toca nisso.
12. **Auditoria e segredos (regra 6).** Evento `auth` no log estruturado (`login`, `failed`, `locked`, `user_added`, `user_disabled`, `credential_created`, `rotated`, `revoked`) com `user_id`, `client_id`, canal e dispositivo; **nunca** o segredo. Mascaramento do padrão `jsk_…` em qualquer saída.
13. **MFA (ADR-021) continua.** Fica por cima: com `auth.mfa.enabled`, a credencial sozinha não abre a sessão, falta o código. O §3 do ADR-021 passa a valer assim: a credencial significa "este dispositivo é desta pessoa". Uma sessão válida continua **sem** autorizar ação `WRITE`/`DESTRUCTIVE` sem o "sim" em palavras (ADR-010).

## Consequências

### Positivas

- Dispositivo e usuário passam a existir como coisas distintas e revogáveis, sem mexer no resto do cérebro.
- Um vazamento do banco não entrega acesso; um vazamento do token antigo some quando o modo legado é desligado.
- A estrutura de `user_id` e `owner_id` já nasce nos dados novos, o que barateia o multiusuário real depois.

### Negativas

- Cada cliente (CLI remota, app, Telegram) precisa de uma atualização para guardar duas chaves em vez de uma; o APK precisa de uma versão nova.
- Perder o segredo obriga a rotacionar; não existe recuperação.
- O banco fora do ar deixa só o dono entrar.
- Um `tester` cadastrado ainda vê o mesmo cérebro; a flag e o aviso existem para isso não ser uma surpresa.

## Alternativas descartadas

1. **Guardar tudo em arquivos (ADR-021 §4):** mais robusto contra o banco cair, mas pedido explícito foi o banco; o espelho do dono cobre o caso de emergência.
2. **Hash lento (argon2/scrypt):** custo sem ganho para um segredo aleatório de 256 bits.
3. **Segredo cifrado de forma reversível:** permitiria mostrá-lo de novo, o que contradiz a regra de aparecer uma vez só.
4. **Credencial no corpo do `welcome`/handshake do protocolo:** mudaria o fluxo do ADR-012; o cabeçalho HTTP já serve e é compatível.
5. **Isolar os dados por usuário agora:** épica própria; aqui só a estrutura.
