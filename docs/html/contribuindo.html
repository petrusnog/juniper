Como contribuir guia

O fluxo de trabalho (issue, branch, PR), as regras de arquitetura, os testes exigidos, as convenções de código e como manter a documentação em dia.

Esta página reúne as regras para quem vai escrever código para a Juniper. O passo a passo para montar o ambiente está em Primeiros passos.

Fluxo de trabalho

Todo trabalho nasce de uma issue do GitHub e termina num pull request para master.

  1. Issue. Cada tarefa tem uma issue com um identificador no título ([T-051] ...), o escopo e os critérios de aceite. Use o modelo de feature (.github/ISSUE_TEMPLATE/feature.md). Tarefas pequenas e incrementais, com critério de aceite claro, são preferidas a mudanças grandes.
  2. Branch. Crie a branch a partir de master, no padrão feature/<TASK>: bash git checkout master && git pull git checkout -b feature/T051
  3. Commits. Prefixe com o identificador da tarefa: T-051: adiciona truncamento de contexto.
  4. Testes e documentação acompanham o código no mesmo PR (veja abaixo).
  5. Pull request direto para master, com o título T-051: <descrição>, a descrição preenchida pelo modelo (.github/pull_request_template.md: o que mudou, a issue com Closes #N e como foi testado).
  6. Merge por squash, mantendo o título do PR: um commit por tarefa em master. A branch é apagada depois.

PRs empilhados (com base em outra branch que não master) não rodam o CI até serem redirecionados para master.

Regras de arquitetura

Estas regras só mudam com um ADR novo (Decisões). Um PR que as quebre não é aceito.

#RegraFundamento
1O núcleo não depende dos clientes: brain/core nunca importa brain/clients.ADR-007
2Cliente fino: captura entrada e mostra saída. Sem lógica de agente, sem acesso ao MongoDB.ADR-012
3Confirmação é conversa, interpretada por brain/core/consent.py, nunca pelo LLM nem pelo cliente. Uma confirmação pendente não sobrevive a retomada, queda ou troca de conexão.ADR-010, ADR-012
4Tools seguem o schema, têm tier READ/WRITE/DESTRUCTIVE/FORBIDDEN e a política de segurança. Tool que roda no dispositivo tem locality = EXECUTOR; o cérebro não escala tier e o cliente revalida tudo. Tool desconhecida do servidor tem piso WRITE.ADR-002, ADR-006, ADR-014
5Protocolo: mudanças compatíveis não mudam protocol_version; o schema gerado (docs/protocol/schema.json) tem de estar em dia.ADR-012
6Segredos só em .env, GitHub Secrets ou arquivos montados; nunca em código, imagem ou log.ADR-003
7Produção: nenhuma porta pública; acesso pela rede privada; o deploy nunca apaga volumes.ADR-013
8Falhas esperadas viram resultado tipado (ToolResult(success=False), error do protocolo), nunca exceção que derruba a conexão ou o servidor.ADR-002, ADR-012
9Um só ponto de configuração: nenhum módulo lê variável de ambiente, YAML ou .env diretamente; tudo vem de brain.config.settings.ADR-003
10Providers trocáveis: o agente fala com LLMProvider, nunca com um provedor específico.ADR-001, ADR-009

Testes

Todo PR que altera código traz testes automatizados funcionais em pytest, cobrindo os critérios de aceite da issue. PRs que alteram apenas docs/ são isentos.

pip install -e ".[dev]"
pytest -m "not integration"   # o que o CI roda
pytest                        # tudo, inclusive integração (MongoDB e modelo reais)
  • Testes que dependem de infraestrutura externa (MongoDB, download de modelo) recebem @pytest.mark.integration e ficam fora do CI padrão.
  • Nenhum teste pode depender de rede, de chave de API real ou do HOME de quem desenvolve: use fixtures e mocks (httpx.MockTransport, providers falsos; veja tests/conftest.py).
  • Testes assíncronos dispensam decorator (pytest-asyncio em modo auto).
  • Mudou o app Android? Rode também npm test, npm run typecheck e npx eslint . dentro de mobile/ (Ambiente mobile).

Qualidade de código

ruff check brain/ tests/    # lint (line-length 100; regras E F I N W UP B C4 SIM)
mypy brain/                 # tipos (strict)

Tiposmypy --strict passa; from __future__ import annotations nos módulos.

SegredosNunca logar nem imprimir chaves, tokens ou senhas. Mensagens de erro são montadas pelo código, nunca copiadas cruas de um SDK.

Definition of Done

Uma tarefa está pronta quando:

  1. Os critérios de aceite da issue são atendidos.
  2. pytest -m "not integration", ruff check brain/ tests/ e mypy brain/ passam.
  3. Há testes novos cobrindo o caminho feliz e os erros.
  4. A documentação (docs/pages) e, se houve decisão de arquitetura, um ADR (docs/decisions/ADR-NNN.md) foram atualizados.
  5. O HTML da documentação foi regenerado (python scripts/build_docs.py).

Decisões de arquitetura (ADRs)

Uma mudança que afete a arquitetura (uma regra acima, o protocolo, o modelo de segurança, a infraestrutura) é registrada como ADR em docs/decisions/ADR-NNN.md, com status, contexto, decisão, consequências e alternativas descartadas. O índice está em Decisões (ADRs). Em escolhas de design com trade-offs reais, apresente as opções na issue antes de implementar.

Documentação

O livro de bolso (docs/html, servido por juniper docs e publicado no GitHub Pages) é gerado: não edite os .html. As fontes são:

  • docs/pages/*.md: as páginas, cada uma começando com title, group, order e description (e, opcionalmente, section, status e tags). Os grupos são as trilhas do menu (Introdução, Ambiente Local, Produto, Documentação Técnica, Referência e Produção). Um título marcado com {#id kind=classe file=caminho} entra no índice de Entidades e na busca;
  • docs/decisions/ADR-*.md: os ADRs (viram adr-NNN.html sozinhos).

Depois de editar uma fonte, rode python scripts/build_docs.py e versione o resultado. O teste tests/test_docs.py falha se o HTML estiver desatualizado, se houver link ou âncora quebrados, se uma página citar um arquivo de tests/ ou scripts/ que não existe ou se uma opção do config.yaml não estiver documentada em Configuração.

Ao escrever: linguagem expositiva, em português, para quem chega sem contexto do projeto. Quando uma página afirma uma regra de comportamento, cite o ADR que a fundamenta.
