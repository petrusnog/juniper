Login com MFA proposto

O login global com segundo fator (TOTP) que vale para todo cliente da Juniper: CLI, Telegram, dashboard e app.

Nota: esta página resume o ADR-021 (proposto). Nada aqui liga o MFA por padrão; ainda é desenho.

Por que

Hoje o WebSocket e o dashboard confiam em um token estático, e o Telegram só em uma lista de IDs. Quem controlar a conta do Telegram fala com a Juniper com todas as tools. A proposta mantém o Telegram completo e fortalece a garantia de que é o dono: uma identidade única, com segundo fator, para todo cliente. Junto com a rede privada (Visão geral da produção), são duas camadas independentes.

Como fica

  • Serviço único brain/auth/: decide quem está autenticado; o cliente só leva a credencial; o LLM nunca vê segredos.
  • TOTP (app autenticador), tolerância de ±1 passo, código usado não vale de novo.
  • O token estático passa a significar "este dispositivo é meu"; com o MFA ligado ele sozinho não basta.
  • Sessão com prazo, ligada ao dispositivo e ao canal, revogável, guardada só como hash em arquivos sob ~/.juniper/auth/ (sem depender do MongoDB).
  • Recuperação: 10 códigos de uso único e, em emergência, juniper auth reset por SSH na VPS. Não existe "esqueci o código" remoto.
ClienteAutenticação
WebSocket (CLI, app)Bearer no handshake + auth.login com o código; até lá a conexão fica "locked".
Telegram/login <código> (a mensagem é apagada), sessão por usuário e chat, expira por inatividade. A lista de IDs vira filtro prévio.
DashboardToken e código; o cookie leva o token de sessão.
VozHerda a conexão; a voz nunca é fator (Voz por áudio).

Usuários e credenciais

O ADR-027 (proposto) acrescenta o usuário (owner ou tester) e troca o token estático por uma credencial client_id + client_secret por dispositivo. O segredo aparece uma vez, no cadastro pela CLI ou pelo dashboard; no MongoDB fica só o hash irreversível (HMAC-SHA256 com um pepper guardado em arquivo). Perdeu o segredo? Rotaciona. Vale para todos os clientes, menos o acesso à VPS. Ainda é desenho, e o multiusuário com isolamento de dados fica para outra épica.

Regras que não mudam

O MFA não substitui a confirmação (Agente). Falha de login é resultado tipado e nunca derruba o servidor. Códigos e tokens de sessão são mascarados no log, com auditoria sem segredos.

Migração

auth.mfa.enabled começa desligado; o usuário cadastra o autenticador e confere tudo com o MFA ainda desligado; só então liga. Desligar é editar o config.yaml por SSH.
