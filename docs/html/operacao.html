Operação e manutenção guia

O dia a dia do servidor: comandos dentro do contêiner, logs, saúde, comandos administrativos da memória, atualização manual, troca de segredos e como recriar tudo do zero.

Usar a Juniper no servidor

Na VPS o comando juniper não existe fora do contêiner: a imagem leva o código e tudo roda dentro do serviço brain (o entrypoint é python -m brain). Crie um atalho no ~/.bashrc do deploy:

echo "alias juniper='docker compose -f ~/juniper/docker-compose.prod.yml exec brain python -m brain'" >> ~/.bashrc
source ~/.bashrc
juniper logs -f               # o log técnico ao vivo
juniper logs --errors         # só falhas
juniper memory list           # a memória do servidor
juniper tools                 # as tools do servidor
juniper voice status          # a voz: credenciais e gasto do mês
juniper music status          # a música: chave, cota e login

Sem terminal interativo (um script, o cron, o CI), use exec -T. Comandos que mexem no ambiente de um computador (install, docs, deploy do git) não fazem sentido no contêiner. O uso do dia a dia é pelos clientes (Clientes em produção).

Saúde e logs

docker compose -f docker-compose.prod.yml ps                 # brain e mongo "healthy"
docker compose -f docker-compose.prod.yml logs --tail=50 brain
curl -s http://<IP-PRIVADO>:8765/health                      # de um dispositivo na rede privada
  • O /health distingue ok e degraded (o modelo de embeddings carregando) (API HTTP).
  • Os logs JSONL ficam no volume juniper-logs, um arquivo por dia, com segredos mascarados; o próprio servidor compacta os de ontem e apaga os com mais de logging.retention_days (3) às logging.rotate_at (00:10) (Observabilidade).
  • Os logs dos contêineres usam o driver json-file com limite de tamanho.
  • Não há alertas ativos: acompanhe a aba Actions (se usa o deploy contínuo) e o ps.

Atualizar

Com o deploy contínuo, um merge em master basta. À mão, com a mesma segurança (backup, healthcheck, rollback), na VPS:

cd ~/juniper && git fetch origin master
./scripts/deploy.sh "$(git rev-parse origin/master)"    # exige a imagem desse SHA no registro

Sem registro de imagens (construindo na própria VPS):

cd ~/juniper && git pull
./scripts/backup_memory.sh manual
docker compose -f docker-compose.prod.yml up -d --build

Mudou só o .env, o config.yaml ou certs/? Basta docker compose -f docker-compose.prod.yml up -d.

Recomeçar do zero

O servidor é descartável: o que importa (a memória) está no backup fora dele. Para recriar:

  1. Reinstale a imagem do sistema no painel do provedor (ou crie uma VPS nova).
  2. Siga Deploy do cérebro numa VPS de cima para baixo e refaça os segredos (eles não estão no backup).
  3. Restaure a memória: Backup da memória → Restaurar.
  4. Remova o nó antigo da rede privada (no Tailscale, em Machines), para o novo reaproveitar o nome.
  5. Se usa deploy contínuo, atualize DEPLOY_HOST e DEPLOY_KNOWN_HOSTS com o IP e a chave do servidor novo.

Atenção: nunca rode docker compose ... down -v num servidor cujos dados não tenham backup: o -v apaga os volumes, inclusive a memória.

Problemas comuns

SintomaOnde olhar
Os clientes não conectamps (o brain está healthy?), a VPN do dispositivo e a varredura de dentro da rede privada.
O cérebro reinicia sem pararlogs brain: credenciais do MongoDB, .env ilegível (uid) ou um arquivo montado que virou pasta.
Respostas lentasOs tempos por etapa no log (timing) e o failover de LLM (failover) (Observabilidade).
A memória não lembrajuniper memory list e juniper memory search "..." --threshold -1 (Memória).
Disco cheiodocker system df; imagens antigas: docker image prune. Nunca apague volumes sem backup.
