API WebSocket pronta

Referência completa do protocolo entre os clientes e o cérebro: conexão, envelope, cada mensagem com os seus campos, erros, códigos de fechamento e reconexão.

Nota: o contrato vem do ADR-012, estendido pelos ADRs 014 (executor) e 023 (voz). A fonte da verdade em código são os modelos de brain/clients/protocol.py, exportados para o JSON Schema docs/protocol/schema.json (python scripts/export_protocol_schema.py). Em caso de divergência, vale o schema. Um guia prático para escrever um cliente está em Integrar com o cérebro.

O token é gerado pelo servidor no primeiro boot e fica no arquivo deployment.auth.token_file (Servidor WebSocket).

Envelope

Toda mensagem tem type. Um pedido do cliente leva um id (único, escolhido por quem pede); a resposta e os eventos ligados a ele levam reply_to com esse id. Campos desconhecidos são ignorados; um type desconhecido gera error com code: "bad_request", sem fechar a conexão.

{ "type": "chat.send", "id": "c-7f3a", "text": "o que tenho amanhã?" }

Handshake

Depois do upgrade, o cliente manda hello e espera welcome.

DireçãotypeCampos
cliente → servidorhelloprotocol_version (int), client {kind, version, device_id, device_name?}, resume? {session_id} ou {latest: true}, trace? (bool)
servidor → clientewelcomeprotocol_version, server_version, heartbeat_seconds, session {id, resumed, turns}
{ "type": "hello", "protocol_version": 1,
  "client": { "kind": "mobile", "version": "0.1.0", "device_id": "mobile-a1b2c3", "device_name": "Celular" },
  "resume": { "latest": true } }
{ "type": "welcome", "protocol_version": 1, "server_version": "4.0.0", "heartbeat_seconds": 30,
  "session": { "id": "20261015-101500-ab12cd", "resumed": true, "turns": 6 } }
  • client.kind identifica o cliente (cli, telegram, mobile...). O servidor usa isso para saber o canal do pedido (Servidor WebSocket).
  • resume leva session_id ou latest: true, nunca os dois nem nenhum (bad_request). Sem resume, o servidor abre uma conversa nova.
  • Versão incompatível: error com unsupported_version e fechamento 4426.
  • Uma segunda conexão com o mesmo device_id substitui a primeira (4409).

Chat

DireçãotypeCamposQuando
cliente → servidorchat.sendid, textUma mensagem do usuário.
servidor → clientechat.startedreply_to, turn_id, session_idO turno começou.
servidor → clientechat.tokenturn_id, textUm pedaço da resposta, em ordem.
servidor → clientechat.endturn_id, finish, usage?, timing?O turno terminou.
cliente → servidorchat.cancelturn_idInterrompe o turno em andamento.

finish é ok, cancelled, max_iterations ou error.

{ "type": "chat.started", "reply_to": "c-7f3a", "turn_id": "t-12", "session_id": "20261015-101500-ab12cd" }
{ "type": "chat.token", "turn_id": "t-12", "text": "Amanhã você tem " }
{ "type": "chat.end", "turn_id": "t-12", "finish": "ok" }
  • Um turno por vez por conversa: chat.send durante um turno recebe turn_in_progress.
  • Confirmação: o cliente não tem estado de confirmação. A Juniper pergunta em palavras dentro de chat.token, e o "sim" é só o próximo chat.send, interpretado pelo cérebro (ADR-010).
  • Queda no meio do turno: o turno termina no servidor e a conversa é salva com a resposta; os tokens não lidos são descartados. Ao retomar, session.state.history traz a resposta completa.

Uma conversa fica ligada a uma conexão por vez. A confirmação pendente não sobrevive a uma queda, a um session.resume (inclusive da própria conversa) nem a outra conexão assumir a conversa.

Executor

Um cliente que cumpre tools no dispositivo (Executor) usa a mesma conexão.

DireçãotypeCampos
cliente → servidorregistertools [{name, description, parameters? (JSON Schema), tier}]
servidor → clienteregisteredtools (as aceitas)
servidor → clienteinvokecall_id, tool_name, arguments, tier?, timeout_ms
cliente → servidorresultcall_id, success, output?, error?, metadata?
{ "type": "invoke", "call_id": "k-9", "tool_name": "open_url",
  "arguments": { "url": "https://music.youtube.com/watch?v=abc" }, "tier": "write", "timeout_ms": 10000 }
{ "type": "result", "call_id": "k-9", "success": true, "output": "Abri o link." }
  • O registro é por conexão: some quando a conexão cai, e o executor se registra de novo ao reconectar (a cada welcome).
  • O cérebro não escala tier: recusa registrar uma tool com tier mais permissivo do que a política que ele já tem para ela, e uma tool desconhecida do servidor tem piso WRITE (ADR-014).
  • O cliente revalida cada invoke (catálogo, schema, tier, política) e responde result com success: false e metadata.code (unknown_tool, invalid_args, tier_mismatch, policy_denied, os_error) quando recusa.
  • Um result que chega depois do timeout_ms é ignorado.

Voz

Extensão compatível do ADR-023: uma sessão de voz por conexão. O áudio vai em quadros de texto JSON com base64 (PCM 16 bits little-endian, mono; seq crescente; de 20 a 100 ms por quadro). Cada fala transcrita vira um turno de chat comum, então a resposta também chega como chat.started, chat.token (a legenda) e chat.end (Voz por áudio).

DireçãotypeCamposQuando
cliente → servidorvoice.startid, format {encoding: pcm_s16le, sample_rate (8000–48000), channels: 1}, local_stt?, local_tts?, route? (speaker, headset)Abre a sessão; format é o do microfone (prefira 16 kHz).
servidor → clientevoice.readyreply_to, input, output, stt, ttsSessão aberta: formatos e se STT e TTS são cloud ou local.
ambosvoice.audioseq, data, turn_id?, last?Do cliente: o microfone. Do servidor: a fala do turno; last fecha a fala.
servidor → clientevoice.statestate (listening, thinking, speaking, idle), turn_id?O que está acontecendo. listening com turn_id = descarte o áudio daquele turno (foi cortado).
servidor → clientevoice.transcripttext, finalO que o usuário disse, como foi entendido.
servidor → clientevoice.sayturn_id, text, last?Fallback de TTS: o aparelho fala o texto.
servidor → clientevoice.fallbackcomponent (stt, tts), mode (local, cloud), reason (quota, budget, error, recovered)Troca de provedor.
cliente → servidorvoice.textid, textFala transcrita no aparelho (fallback de STT).
cliente → servidorvoice.interrupt—Calar a Juniper agora.
cliente → servidorvoice.routerouteA saída de áudio mudou (fone ligado ou desligado).
ambosvoice.endreason (client, command, silence, error, server)Encerra a sessão.

voice.audio e voice.end valem nos dois sentidos; as demais só na direção da tabela (a outra recebe bad_request). Base64 inválido ou seq fora do limite também é bad_request. Em route: speaker, o servidor ignora o microfone enquanto a Juniper fala (e por 1 s depois).

Erros

{ "type": "error", "reply_to": "c-7f3a", "code": "llm_unavailable", "message": "Não consegui falar com nenhum LLM agora.", "retryable": true }

message é o texto amigável em português; code é para o programa decidir. A conexão continua aberta depois de qualquer erro de pedido; um erro de turno também fecha o turno com chat.end (finish: "error").

Reconexão

  • Recuo exponencial com variação: 1, 2, 4, 8, 16 e depois 30 s (±20%); zera depois de 30 s de conexão estável. Em 1012, reconecta quase na hora. 4401, 4409 e 4426 param e mostram o motivo.
  • Ao reconectar, manda hello com a conversa que estava aberta e, se for executor, repete o register.
  • Offline, o cliente não enfileira mensagens: avisa que a Juniper está indisponível e mantém o texto digitado.
