T-021 — Registry de Tools

A lista de tools da Juniper, que se monta sozinha. Quem cria uma tool só escreve a classe e coloca @register_tool em cima; ninguém edita uma lista central. Arquivo: brain/tools/registry.py.

1. O que ele faz

Arquivo da tool@register_tool na classe
→
registrynome → classe
→
Dispatcherget(nome) (T-030)
→
LLMschemas()

O registry guarda classes, não instâncias. O dispatcher cria a instância na hora de executar. O LLM só enxerga o que o registry devolve em schemas().

2. Uso

Registrar uma tool

from brain.tools.base import Tool, ToolResult
from brain.tools.registry import register_tool

@register_tool
class ListEvents(Tool):
    name = "list_events"
    description = "..."
    parameters = {...}
    async def run(self, **kw): ...

Consultar

from brain.tools.registry import registry

registry.discover()            # na partida
registry.get("list_events")    # classe ou None
registry.all()                 # todas as classes
registry.schemas()             # para o campo tools do LLM

3. Auto-descoberta

registry.discover() importa todos os módulos de brain/tools/. Importar um módulo executa o @register_tool das classes dele, e é assim que a tool entra na lista.

MóduloO que acontece
base e registryIgnorados: são infraestrutura, não registram nada.
Nome começando com _Ignorado: convenção de módulo privado.
Qualquer outro (web.py, google_calendar.py…)Importado. Se tiver tools decoradas, entram no registry.

Tool nova = arquivo novo. Basta criar o arquivo em brain/tools/. O teste da task faz exatamente isso, com um pacote temporário.

4. Erros

nome já registrado por outra classeDuas tools com o mesmo name confundiriam o LLM.ValueError
não é uma subclasse concreta de ToolRegistrar a classe abstrata Tool ou qualquer outra coisa.TypeError
módulo de tool que não importaDependência faltando ou erro no arquivo. Falha alto na partida em vez de sumir da lista.ImportError
get() de nome desconhecidoDevolve None. O dispatcher (T-030) transforma isso em ToolResult(success=False) para o LLM.None

Registrar de novo a mesma classe (por exemplo, ao recarregar um módulo) não é erro.

5. Decisões proativas

#DecisãoPor quê
1Há um objeto registry e o decorator register_tool aponta para ele.Combina com a spec (registry.get(...)) e deixa criar registries separados nos testes (ToolRegistry()).
2get() devolve None em vez de levantar erro.Tool desconhecida é caso esperado: o LLM pode inventar um nome. O dispatcher trata sem try/except.
3Erro de importação na descoberta propaga.Uma tool quebrada que some em silêncio é pior que um erro claro na partida.
4discover() é explícito (ninguém chama sozinho).Fica visível quando a descoberta acontece. O agente (T-030) vai chamá-lo na partida; esquecer significa registry vazio.
5discover(package=...) aceita outro pacote.Permite testar com um pacote temporário, como a spec pediu.
6A validação dos metadados fica na T-020 (Tool.__init_subclass__).O registry não repete checagem: quando a classe chega aqui, já foi validada.

6. Limitações conhecidas

Estado global. O registry padrão é um objeto do módulo. Os testes isolam isso trocando o conteúdo dele; em código normal, ele vive o processo inteiro.

Sem desregistro. Não há unregister: tools só entram. Não fez falta até agora.

Ordem de descoberta. Segue a ordem em que o Python lista os módulos; all() e schemas() não prometem ordem estável entre arquivos.

Tools remotas (Sprint 5). Executores anunciarão suas tools por WebSocket (ADR-007). Esse catálogo dinâmico ainda não existe e será tratado nessa época.

7. Como testar

pytest tests/test_tools_registry.py -v

Cobre: registrar e consultar, get() desconhecido, all()/schemas(), nome duplicado, registro idempotente, classe abstrata e não-tool rejeitadas, o decorator no registry global, e a auto-descoberta com pacotes temporários (arquivos novos aparecem sem lista central, módulos base/registry/_privados são ignorados e erros de importação propagam).
