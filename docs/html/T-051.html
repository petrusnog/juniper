T-051 — Memória de sessão

A memória de curto prazo: a Juniper lembra da conversa que está acontecendo, não estoura o limite do LLM e, se você fechar o terminal, pode retomar de onde parou. Arquivos: brain/core/session.py e brain/memory/session.py. Decisões de fundo no ADR-011.

1. Uso

juniper                  # conversa nova (a anterior fica guardada)
juniper --resume         # retoma a conversa mais recente  (atalho: -r)
juniper -r "e o prazo?"  # retoma e já manda uma mensagem

Toda conversa é salva sozinha ao fim de cada turno. Sem conversa anterior, --resume avisa e abre uma nova.

2. Como funciona

PeçaO que faz
SessionGuarda o histórico, mais um id (ordenável por data) e os horários de criação e atualização.
Orçamento de tokensAntes de cada pedido ao LLM, compact() mantém o histórico dentro de memory.session.max_tokens. Os tokens são estimados (≈ 4 caracteres cada), sem tokenizer.
SessionStoreA interface que o Agent usa para salvar: save, load, latest, list_sessions.
FileSessionStoreUm arquivo JSON por conversa em ~/.juniper/sessions/. O MongoDB entra na T-053 trocando só esta peça.
AgentSalva depois de cada turno, inclusive quando o turno falha (já desfeito pelo rollback).

3. O que sai quando passa do limite

Primeiro vale o teto de turnos (max_turns). Depois, se o histórico ainda passa de max_tokens, saem os turnos mais antigos, inteiros: a sua mensagem e tudo que veio depois dela, chamadas de tool incluídas. Assim nunca sobra uma resposta de tool sem a chamada que a originou, que o LLM recusaria. O turno em andamento nunca é descartado.

Não há resumo por LLM nesta etapa: seria uma chamada a mais a cada estouro. O que importa de uma conversa antiga vira memória de longo prazo, nas próximas tasks da Sprint 2.

4. Configuração

memory:
  session:
    max_turns: 8            # turnos seus mantidos
    max_tokens: 6000        # orçamento estimado do histórico
    dir: ~/.juniper/sessions

5. Privacidade

A conversa inteira fica em disco, então a pasta é só sua (permissão 700, arquivos 600). A escrita é atômica: uma queda no meio deixa a versão anterior, nunca um arquivo pela metade.

Dois cuidados ao retomar: a persona não é salva (vale a atual) e uma confirmação pendente não volta. Se a Juniper tinha perguntado "posso apagar?", depois de retomar nada é executado sem um novo "sim" (ADR-006).

6. Decisões proativas

#DecisãoPor quê
1Arquivos agora, MongoDB depois.O Mongo só chega na T-053. A interface SessionStore deixa a troca sem mexer no resto.
2Falha ao salvar não derruba a conversa.Disco cheio ou sem permissão vira um evento error no log; você continua conversando.
3Ids validados ([A-Za-z0-9_-]).O id vira nome de arquivo; sem isso, ../algo escaparia da pasta.
4Arquivo estragado é ignorado ao buscar a conversa mais recente.Um JSON corrompido não pode esconder as conversas boas.
5list_sessions, e não list.Um método chamado list conflita com o tipo list[...] no mypy estrito.

7. Limitações conhecidas

Retoma só a mais recente. Escolher outra conversa pela lista (list_sessions já existe) fica para quando houver o juniper memory.

Sem expiração. As conversas ficam até você apagar os arquivos.

Estimativa de tokens é aproximada. Texto com muito código ou emoji pode pesar mais que o previsto; o orçamento padrão tem folga para isso.

8. Como testar

pytest tests/test_session_memory.py -v

Cobre: orçamento (descarta turnos inteiros, preserva o atual, não deixa tool órfã), serialização, arquivo (ida e volta, permissões, escrita atômica, id malicioso, arquivo corrompido, mais recente), o agente lembrando, salvando e retomando, turno com falha, disco quebrado e o --resume no CLI.

Para ver ao vivo: juniper "meu projeto X usa Laravel 11", feche, depois juniper -r "que framework o X usa?".
