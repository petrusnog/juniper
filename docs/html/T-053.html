T-053 — MongoDB e Docker Compose

Um banco local para as conversas: docker compose up -d sobe o MongoDB e a Juniper passa a guardar nele o que antes ia para arquivos. Se o banco estiver fora do ar, ela avisa o que fazer em vez de mostrar um erro técnico. Arquivos: brain/memory/mongo.py, brain/memory/stores.py, brain/memory/errors.py e docker-compose.yml. Decisões de fundo no ADR-011.

1. Como ligar

Requisito: Docker. O MongoDB roda num container, então é preciso ter o Docker (com o plugin docker compose) instalado e rodando nesta máquina. Sem Docker, use store: file (o padrão): as conversas ficam em JSON na pasta sessions/ e nada mais é necessário.

Jeito fácil: o instalador pergunta onde guardar a memória e, se você escolher o MongoDB, confere o Docker, sobe o banco, cria o usuário e a senha no .env e liga o store: mongo sozinho. Para fazer isso depois: juniper install --memory=mongo (veja o guia de instalação).

Se preferir fazer à mão:

# 1. .env  (nunca é versionado): escolha usuário e senha do banco
JUNIPER_MEMORY__MONGO__USERNAME=juniper
JUNIPER_MEMORY__MONGO__PASSWORD=uma-senha-forte

# 2. sobe o banco
docker compose up -d

# 3. config.yaml
memory:
  session:
    store: mongo

Depois disso juniper e juniper -r funcionam como antes; só o lugar onde a conversa fica muda. Para voltar aos arquivos, basta store: file (o padrão).

Não troque usuário e senha depois de subir. O Mongo só lê essas variáveis quando cria o volume. Para recomeçar com outras credenciais: docker compose down -v (apaga os dados) e docker compose up -d.

As conversas antigas não migram. Os JSONs de ~/.juniper/sessions/ continuam lá, mas com store: mongo o --resume só enxerga o banco.

2. Como funciona

PeçaO que faz
scripts/install.shPergunta arquivos ou MongoDB. Com MongoDB: confere o Docker, gera as credenciais, sobe o banco, testa a conexão e só então grava store: mongo (via scripts/set_memory_store.py, que preserva os comentários do config.yaml). Sem Docker, fica em arquivos e diz o motivo.
docker-compose.ymlSobe o mongo:7 só em 127.0.0.1:27017 (a rede nunca vê o banco), com volume juniper-mongo-data e healthcheck. Usuário e senha vêm do .env; sem eles o compose recusa subir.
MongoConnectionCria o cliente só quando preciso, faz o teste de saúde (check()) e traduz qualquer falha do driver em MemoryUnavailableError.
MongoSessionStoreImplementa o SessionStore da T-051 (save, load, latest, list_sessions). O Agent não sabe que mudou.
open_session_store()Escolhe o store pelo memory.session.store. Com mongo, já faz o teste de saúde: é o healthcheck de inicialização.
MemoryUnavailableErrorErro com mensagem escrita para você, em português, dizendo o que fazer. O CLI a imprime e sai com código 1, sem stacktrace.

brain/memory/mongo.py é o único arquivo que importa o driver (pymongo), e ele só é carregado quando store: mongo. Quem usa arquivos nunca depende dele.

3. O que fica no banco

Banco juniper, collection sessions, um documento por conversa. É o mesmo conteúdo do JSON, mais alguns campos auxiliares:

{
  "_id": "20261014-034312-b94e9d",      // o id da sessão: um documento por conversa
  "version": 1,
  "created_at": "2026-10-14T03:43:12+00:00",
  "updated_at": "2026-10-14T03:44:02+00:00",
  "history": [ {"role": "user", "content": "..."}, {"role": "assistant", "content": "..."} ],
  "turns": 1,                           // para listar sem ler o histórico
  "preview": "[...] meu projeto X usa Laravel 11",
  "saved_at": "2026-10-14T03:44:02.123456+00:00"
}
QuandoO que acontece
Fim de cada turnoreplace_one com upsert: o documento inteiro é substituído. Se o turno falhou, ele já foi desfeito e o salvo continua igual ao da memória.
Sessão vaziaNão grava nada.
Gravação falhaVai para o log (evento error) e a conversa continua.
--resumePega a conversa de maior saved_at. Retomar e salvar uma conversa antiga a torna a mais recente de novo, igual ao que o mtime fazia nos arquivos.

Como em arquivos, só o histórico é guardado: a persona não entra (vale a atual) e confirmação pendente não volta (ADR-006). Há dois índices, em saved_at e em updated_at + saved_at, criados na primeira gravação.

4. Configuração

memory:
  session:
    store: file          # file (padrão) ou mongo
  mongo:
    uri: mongodb://localhost:27017
    database: juniper
    timeout_ms: 3000     # quanto esperar pelo servidor antes de avisar que caiu

Usuário e senha ficam só no .env (ADR-003), como JUNIPER_MEMORY__MONGO__USERNAME e JUNIPER_MEMORY__MONGO__PASSWORD. O mesmo par é lido pelo compose, então há uma única fonte. A senha é entregue ao driver à parte, sem ir na URI: caracteres como @, : e / não precisam de escape.

5. Quando o banco não está lá

SituaçãoO que você vê
Banco fora do ar"Não consegui conectar ao MongoDB em mongodb://localhost:27017. Suba o banco com docker compose up -d, ou guarde as conversas em arquivos com memory.session.store: file no config.yaml."
Usuário ou senha errados"O MongoDB recusou o usuário ou a senha." com os nomes das variáveis a conferir.
Driver não instaladoPede pip install -e ..

Em todos os casos a Juniper sai com código 1 antes de falar com o LLM. Se o banco cair no meio da conversa, só a gravação falha (vai para o log) e a conversa segue.

6. Decisões proativas

#DecisãoPor quê
1Banco fora do ar = avisa e sai, sem cair para arquivos em silêncio.Um fallback silencioso gravaria conversas num lugar que você não espera. Quem quiser arquivos escolhe store: file.
2Credenciais fora da URI, na SecretStr.Não aparecem em repr nem em mensagem de erro, e senhas com símbolos não precisam de escape.
3saved_at com microssegundos para achar a mais recente.O updated_at tem precisão de segundos e empata; o saved_at reproduz a ordem por mtime dos arquivos.
4Driver só importado com store: mongo.Os arquivos continuam sem dependência do Mongo, e o resto do código nunca vê o pymongo.
5Porta presa em 127.0.0.1.O banco não fica exposto na rede.
6Documento corrompido é ignorado em latest e list_sessions.Igual ao arquivo estragado: um registro ruim não esconde as conversas boas.

7. Limitações conhecidas

Ainda é só o histórico. Não há embeddings nem fatos extraídos: a collection memories do ADR-011 vem nas T-054 a T-058. Sem --resume, uma conversa nova começa sem saber nada de você.

O histórico é limitado por max_turns e max_tokens, e o documento é substituído a cada turno: o que saiu do histórico sai também do banco.

Chamadas síncronas. Com o banco fora do ar, cada gravação pode esperar até timeout_ms (3 s) antes de falhar.

Sem migração dos JSONs antigos, e sem expiração: as conversas ficam até você apagar.

8. Como testar

pytest -m "not integration"     # sem banco: o que o CI roda
pytest -m integration           # contra o MongoDB local (docker compose up -d)

Os testes sem banco cobrem a configuração, as mensagens de erro (banco fora do ar, senha recusada), a escolha do store e o CLI sem stacktrace. Os de integração rodam o mesmo contrato do FileSessionStore contra o MongoSessionStore (tests/test_session_store_contract.py), mais os casos próprios do Mongo (tests/test_mongo_store.py). Cada teste usa um banco descartável e o apaga no fim, então suas conversas reais não são tocadas.

Para olhar os dados: docker exec -it juniper-mongo mongosh -u <usuario> -p --authenticationDatabase admin juniper, depois db.sessions.find({}, {history: 0}). Atenção ao banco: sem o juniper no fim, o mongosh abre o banco test, que está vazio.
