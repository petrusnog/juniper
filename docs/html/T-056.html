T-056 — Extração de memórias

Ao fim de uma conversa, a Juniper separa o que vale lembrar (suas preferências, seus projetos, fatos duráveis) e guarda no MongoDB. Ela não duplica o que já sabe, atualiza o que mudou e nunca guarda segredos. Arquivos: brain/memory/extraction.py, brain/memory/secretfilter.py e brain/memory/longterm.py. Decisões de fundo no ADR-011.

1. Quando ela roda

Ao encerrar o chat (/sair, Ctrl+D, ou depois de uma mensagem isolada), ela olha os turnos da conversa e guarda o que valer. Se guardar algo, avisa: "Guardei 2 coisas sobre você para a próxima." Se não houver nada, fica quieta.

Só funciona com memory.session.store: mongo (é lá que as memórias ficam) e com memory.extraction.enabled: true (o padrão). Com arquivos, nada muda. O modelo de embeddings (~120 MB) só é baixado quando houver mesmo algo a guardar.

2. O que acontece com cada fato

EtapaO que faz
1. ExtrairUm LLM (o mesmo do chat) lê os turnos e devolve fatos curtos, cada um com tipo (preference, project ou fact). Pedidos pontuais, conversa social, saídas de comandos e conteúdo da web não entram.
2. FiltrarDescarta o que parece segredo, pergunta, ordem para uma IA, ou passa de max_chars.
3. CompararBusca as memórias mais parecidas já guardadas. Texto igual = duplicata. Se há parecidas, o LLM decide: duplicate, supersede ou new.
4. Gravarnew: cria a memória. duplicate: só atualiza updated_at da existente. supersede: cria a nova e marca a antiga como superseded, apontando para a nova (a busca só enxerga a ativa).

Nada é editado no lugar e nada é apagado: apagar é só pelo forget (T-058). Se o LLM responder algo inválido ou apontar para uma memória que não estava entre as comparadas, a regra é guardar o fato como novo.

3. Segredos

O filtro (secretfilter.py) reconhece chaves de API (sk-, gsk_, ghp_, AWS...), tokens JWT e Bearer, chaves privadas, credenciais em URL, sequências longas que parecem token, números de cartão (com checagem Luhn) e "senha/token/cvv ... é/=/: valor".

Ele age duas vezes: mascara a conversa antes de mandá-la ao LLM de extração e recusa candidatas que pareçam segredo depois. Em dúvida, recusa.

É uma heurística, não uma garantia. Uma senha colada no chat continua no arquivo da sessão (veja o ADR-011, seção 6), e um segredo num formato que o filtro não conhece pode passar.

4. Configuração

memory:
  extraction:
    enabled: true
    max_per_run: 5          # memórias novas, no máximo, por conversa
    max_chars: 300          # tamanho máximo de cada memória
    max_turns: 20           # turnos recentes enviados ao LLM
    neighbors: 3            # memórias parecidas comparadas antes de gravar
    neighbor_threshold: 0.75

5. Limitações conhecidas

O trecho analisado vai ao provider do chat (DeepInfra, Groq ou Ollama), como a própria conversa. Só o embedding é local. Com os segredos já mascarados.

Ctrl+C derruba o chat sem extrair. A extração roda na saída normal (/sair, Ctrl+D). Se o terminal for fechado à força, as memórias daquela conversa se perdem.

A qualidade depende do LLM. Ele pode guardar o que não devia ou deixar de guardar. O juniper memory list/forget (T-058) existe para você auditar e apagar.

Não testado com um LLM e um banco reais. Os testes usam um LLM roteirizado e uma collection falsa; o texto dos prompts e o neighbor_threshold (0.75) precisam ser calibrados com uso real.

6. Como testar

pytest -m "not integration"   # CI: sem LLM, sem banco, sem modelo
