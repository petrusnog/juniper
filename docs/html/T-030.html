T-030 — Agent loop, Dispatcher e Session

O cérebro que junta tudo: recebe o que você disse, pergunta ao LLM, executa as tools que ele pedir (com a sua confirmação quando necessário) e repete até haver uma resposta final. Arquivos: brain/core/agent.py, dispatcher.py e session.py.

1. O que cada peça faz

ClienteCLI (T-040)
→
Agentrun(texto)
⇄
LLMrouter (T-015)
→
Dispatchertier + confirmação
→
Toolregistry (T-021)
PeçaResponsabilidade
SessionGuarda o histórico e o prompt de sistema (prompts/juniper.md). Marca a data e hora em cada mensagem sua. Enxuga o histórico para economizar tokens.
DispatcherPega um ToolCall do LLM e devolve uma Message(role="tool"). Valida, checa o tier, pede confirmação e executa. Nunca levanta exceção: todo problema volta ao LLM como texto.
AgentO loop em si: chama o LLM, repassa as tool calls ao dispatcher, devolve os resultados ao LLM e repete. Limitado por agent.max_iterations (padrão 5).

2. O loop de um pedido

#Passo
1O Agent anota na Session sua mensagem, com [domingo, 11/10/2026, 17:30 (America/Sao_Paulo)] na frente, e compacta o histórico.
2Chama o LLM com stream, mandando persona + histórico + schemas das tools. Cada pedaço de texto vai na hora para o cliente (on_token).
3Se o LLM respondeu sem tool calls, acabou: devolve o texto.
4Se pediu tools, o Dispatcher executa cada uma e os resultados entram no histórico. Volta ao passo 2.
5Se chegar a max_iterations voltas ainda pedindo tools, a Juniper para e avisa que deu voltas demais.

3. Como o Dispatcher decide

tool desconhecidaO LLM pode inventar um nome. Volta como erro, para ele corrigir.erro ao LLM
tier FORBIDDENNunca executa e nem pergunta a você.bloqueada
argumentos inválidosObrigatório ausente, argumento desconhecido ou tipo errado (true não vale como inteiro).erro ao LLM
precheck falhaA tool recusa antes de te incomodar (ex.: conflito na agenda). Você não é perguntado.erro ao LLM
tier WRITE / DESTRUCTIVEChama o callback de confirmação. Negado, expirado ou ausente = não executa.confirma
tier READExecuta direto.executa
tool levanta exceçãoSó o nome do tipo vai ao LLM (falha interna da ferramenta (KeyError)); a mensagem pode ter segredos. O detalhe vai ao log.erro ao LLM

4. Uso

from brain.core.agent import Agent
from brain.core.dispatcher import Dispatcher
from brain.llm.router import LLMRouter
from brain.tools.registry import registry

registry.discover()

async def confirm(tool, args, tier) -> bool:   # o cliente decide como perguntar
    ...

agent = Agent(LLMRouter(), Dispatcher(confirm))
resposta = await agent.run("marca dentista amanhã às 16h", on_token=print)

on_token pode ser função comum ou async. O core nunca chama input() nem importa de clients/: quem sabe perguntar é o cliente.

5. Decisões proativas

#DecisãoPor quê
1Confirmação é um callback async confirm(nome, args, tier) -> bool, com timeout de confirmation_timeout.Mantém o core agnóstico de transporte; CLI, celular ou voz implementam do jeito deles.
2Sem callback = nega. Timeout = nega.Na dúvida, nunca agir sem você.
3Prompt de sistema fixo; data e hora vão na mensagem do usuário.Prefixo idêntico entre chamadas permite ao provider reaproveitar cache e poupa tokens do limite gratuito da Groq.
4Sempre stream, mesmo sem on_token.Um só caminho de código; sem callback, os pedaços só são juntados.
5Se o LLM falha, o turno é desfeito (rollback da Session) e o erro sobe.Tentar de novo não vê meia conversa. O cliente decide como mostrar o erro.
6Compactação: guarda os últimos 8 turnos; só o turno atual e o anterior mantêm as mensagens de tool.O anterior preserva ids ("apaga esse evento"); o resto vira só conversa. Veio do script try_calendar.py.
7Regras de agenda foram para prompts/juniper.md.Antes viviam no script de teste; agora fazem parte da persona.

6. Limitações conhecidas

Ninguém chama o Agent ainda. O juniper é um placeholder até a T-040, e o try_calendar.py ainda usa seu próprio loop.

Tools em sequência. Várias tool calls da mesma resposta rodam uma após a outra, não em paralelo, para as confirmações não se misturarem.

Sem log estruturado. Só logging comum por enquanto; os eventos em JSONL são a T-031.

Memória só da sessão. O histórico vive no processo e some ao encerrar (memória persistente é Sprint 3).

Validação de argumentos é rasa. Checa presença, nome e tipo do nível de cima, não schemas aninhados; a tool continua responsável por validar o conteúdo.

7. Como testar

pytest tests/test_agent.py -v

Usa um FakeProvider roteirizado e tools falsas, sem rede. Cobre: resposta direta com streaming (síncrono e async), uma tool call, tool calls encadeadas, limite de iterações, confirmação concedida, negada, expirada e sem callback, READ sem confirmação, FORBIDDEN, tool desconhecida, argumentos inválidos, exceção sem vazar mensagem, rollback quando o LLM falha e compactação da Session.
