T-062 — Memória silenciosa e medição de tempo

Duas mudanças pedidas ao usar a memória de longo prazo: guardar sem perguntar, para a conversa fluir, e medir onde o tempo vai, para saber o que está lento (o embedding local, o LLM, o banco) em vez de adivinhar. Arquivos: brain/timing.py, brain/tools/memory.py, brain/core/agent.py, brain/memory/extraction.py.

1. Guardar não pergunta mais

Antes, remember e update_profile eram escritas com confirmação: a Juniper perguntava "posso guardar...?" e esperava o seu "sim". Agora gravam na hora, sem perguntar. A diretriz também saiu da persona: ela chama a tool direto e, no máximo, diz "anotado".

Como você acompanha: juniper memory list mostra o que ela sabe, forget apaga e profile mostra e corrige o perfil. A extração do fim do chat já era automática.

O que continua pedindo confirmação: só o forget, que é irreversível. Segredos, ordens e texto grande continuam recusados mesmo sem perguntar.

O risco que se aceita: como ninguém aprova, algo plantado numa página da web que o LLM leu pode virar memória. Ele é limitado pelo filtro de segredos e de ordens e por as memórias entrarem no prompt sempre como dado, nunca como ordem; e você audita e apaga quando quiser.

Tecnicamente: uma tool WRITE pode declarar confirm = False. Só WRITE pode; uma tool DESTRUCTIVE que tente é recusada ao ser carregada.

2. Medindo onde o tempo vai

JUNIPER_AGENT__SHOW_TIMING=true juniper         # mostra no terminal (ou show_timing: true no config.yaml)

Depois de cada resposta aparece uma linha apagada, e no fim do chat uma da extração:

⏱ total 2.4s · memória 210ms · LLM 1.9s · 1ª palavra 780ms · salvar sessão 4ms  [memória: embedding 160ms · busca 40ms]

⏱ memória (extração) total 6.1s · LLM extração 2.2s · carga do modelo 1.4s · embedding 90ms
   · busca 12ms · LLM julgamento 2.1s · gravação 18ms · 2 chamada(s) ao LLM
EtapaO que é
memóriaBuscar o perfil e as memórias da sua mensagem. Aberta em: perfil (leitura no banco), contagem, carga do modelo (única vez por processo), embedding (transformar a pergunta em vetor, local, na CPU) e busca (ler e comparar os vetores).
LLM / 1ª palavraTempo total do LLM e até ele começar a responder.
ferramentasExecução das tools (agenda, git, memória...).
salvar sessãoGravar a conversa.
extração (fim do chat)LLM extração (uma chamada), LLM julgamento (uma por memória nova parecida com alguma já guardada), carga do modelo e embedding (um por memória candidata), busca e gravação.

Etapas abaixo de 1 ms não aparecem. Tudo isso também vai para o log estruturado (~/.juniper/logs/AAAA-MM-DD.jsonl), mesmo com show_timing desligado:

# cada resposta e cada extração
jq -c 'select(.event=="timing") | {scope, total_ms, stages_ms}' ~/.juniper/logs/*.jsonl

# o embedding local: tempo de inferência por chamada e a carga do modelo
jq -c 'select(.event=="embedding" or .event=="embedding_model_load")' ~/.juniper/logs/*.jsonl

3. Como ler o resultado

Estas são hipóteses a partir do código, não medições (não consegui rodar com o modelo e o LLM reais). Os números do seu uso dizem qual vale.

O que apareceQuer dizer
carga do modelo alta, só uma vezÉ o custo de abrir o modelo de embeddings na primeira vez do processo. Acontece uma vez por chat, não por mensagem.
embedding alto em toda mensagem (centenas de ms)É a CPU local. Teste memory.embeddings.threads: menos threads aliviam a máquina; veja no log (embedding, infer_ms) o efeito.
LLM julgamento e LLM extração altos no fim do chatÉ rede e provider, não a máquina local. Cada memória nova parecida com uma antiga custa uma chamada a mais, uma depois da outra.
busca altaLer os vetores do MongoDB; cresce com o número de memórias.
1ª palavra altaO provider demora para começar (ou houve failover).

Por que o fim do chat parece travar: a extração roda depois do "Até logo!", e antes não mostrava nada. Agora aparece "guardando o que aprendi..." enquanto trabalha.

4. Configuração

agent:
  show_timing: false        # mostra o tempo de cada etapa no terminal
memory:
  embeddings:
    threads: 0              # CPU do onnxruntime; 0 = automático (todos os núcleos)

5. Limitações conhecidas

A extração ainda roda ao sair, e você espera por ela. Esta task só mostra o que está acontecendo e onde. Se os números mostrarem que ela é o gargalo, o próximo passo é extrair em segundo plano durante o chat.

Os tempos são de relógio (wall-clock): com a máquina ocupada, qualquer etapa pesa mais. Compare várias respostas, não uma.
