Contexto

Com o cérebro na VPS, as coisas que a Juniper faz na máquina do usuário (abrir uma página no navegador, abrir um aplicativo, rodar um comando) não podem rodar no servidor. O ADR-007 criou a ideia do executor: um processo no dispositivo que anuncia suas capacidades como tools remotas e cumpre os pedidos do cérebro. Faltam as regras concretas: onde o executor roda, o que o cérebro pode mandar, o que o cliente confere antes de obedecer e como a primeira tool (open_url) se comporta.

Decisões do usuário para a Sprint 3: o executor do PC fica dentro do Electron (não é um processo separado), o cérebro manda comandos estruturados (nunca scripts) e o cliente revalida o que recebe. Exemplo que motivou o desenho: "abre o YouTube Music no navegador e toca She Said She Said": o cérebro diz o que quer (uma URL ou uma intenção) e o cliente tem os mecanismos para fazer.

A Sprint 3 só precisa provar a arquitetura: chat por texto mais uma tool de executor, open_url. As outras tools (media_play, open_app, run_shell) vêm depois.

Decisão

1. Onde o executor roda

  • No processo principal do Electron (Node), o mesmo app que mostra o chat (ADR-015). Um app instalado, uma conexão WebSocket (ADR-012, seção 9).
  • O CLI remoto também pode ser executor enquanto estiver conectado: registra git_search e git_deploy (seção 9). O contrato é o mesmo.
  • Um cliente só de chat (sem executor) não registra tools e não recebe invoke.

2. Comandos estruturados, não scripts

O cérebro nunca manda código, comandos de shell soltos ou caminhos arbitrários. Ele manda o nome de uma tool declarada e argumentos validados por JSON Schema:

{ "type": "invoke", "call_id": "k-9", "tool_name": "open_url",
  "arguments": { "url": "https://www.youtube.com" }, "timeout_ms": 10000 }

Como cumprir é decisão do cliente (qual navegador, qual API do sistema). Isso mantém o cérebro sem conhecer o dispositivo e limita o que um LLM induzido por conteúdo malicioso consegue pedir.

3. Registro e catálogo

  • Depois do welcome (ADR-012), um executor manda register com tools[]: nome (snake_case, ADR-002), description em PT-BR, parameters (JSON Schema) e tier (ADR-006). O brain responde registered.
  • O catálogo é por conexão: some quando a conexão cai ou o heartbeat expira (90 s). Ao reconectar, o executor repete o register.
  • As tools de executor entram no ToolRegistry do brain como entradas dinâmicas com locality = EXECUTOR (ADR-007). Para o LLM são tools como as outras (to_schema()).
  • O brain não escala tier. Só despacha uma tool com o tier que o executor declarou, e o Dispatcher aplica a política do ADR-006 como em qualquer tool. O executor não pergunta nada ao usuário: a confirmação é a conversa (ADR-010), feita no cérebro com o cliente que originou o pedido.

4. Roteamento (qual executor recebe o invoke)

  1. O executor da mesma conexão que originou o turno, se ele oferece a tool.
  2. Senão, se exatamente um executor conectado oferece a tool, esse.
  3. Senão, se mais de um oferece e nenhum é o originador, o brain não escolhe: devolve um ToolResult(success=False) listando os nomes dos dispositivos, e a Juniper pergunta ao usuário qual usar.
  4. Senão (nenhum oferece), ToolResult(success=False) com a mensagem de "dispositivo indisponível" (seção 7).

O nome do dispositivo (device_name) é o que a Juniper usa ao falar com o usuário ("no PC do Petrus").

5. Revalidação local obrigatória (o cliente não confia no cérebro)

Antes de executar qualquer invoke, o executor confere, nesta ordem:

  1. A tool existe no seu catálogo declarado (senão: unknown_tool).
  2. Os argumentos obedecem ao JSON Schema da tool, incluindo tipos (senão: invalid_args).
  3. O tier recebido bate com o declarado (senão: tier_mismatch).
  4. A política da tool (seção 6) aceita os argumentos (senão: policy_denied).

Qualquer recusa devolve um result com success: false, um error em PT-BR para o LLM explicar ao usuário e um metadata.code; e vai para o log local do cliente (sem segredos). Nada é executado "para ver se dá certo".

Conteúdo vindo da web é dado, nunca instrução (ADR-006): o cérebro pode ter lido uma página que tenta induzi-lo a abrir uma URL. As defesas são, juntas, a revalidação do cliente, a lista de domínios e a confirmação na conversa que mostra a URL exata.

6. A tool open_url

CampoValor
Nomeopen_url
Parâmetrosurl (string, obrigatória)
LocalityEXECUTOR
TierWRITE
Descrição (para o LLM)"Abre uma página no navegador padrão do dispositivo do usuário. Use quando ele pedir para abrir um site, uma busca ou um vídeo."

Política de URL (vale no brain e de novo no cliente):

  • Só esquemas http e https. file:, javascript:, data:, ftp:, vbscript:, esquemas de aplicativos e qualquer outro são recusados.
  • Sem credenciais embutidas (usuario:senha@host).
  • URL com até 2.048 caracteres, sem caracteres de controle; é normalizada antes de conferir.
  • Nome de domínio comparado na forma ASCII (punycode), para o domínio de uma lista não ser imitado com letras parecidas (IDN).
  • Hosts locais e privados são recusados: localhost, endereços de loopback, de rede privada, de link-local e a faixa do Tailscale (100.64.0.0/10), quando o host é um IP ou o nome localhost. A resolução de DNS não é feita na política (um DNS que aponta para um endereço privado passa; risco aceito, o navegador do usuário é quem abre) [a confirmar].

Confirmação. Por padrão, open_url pede confirmação na conversa mostrando a URL exata ("Posso abrir https://...?"), como toda tool WRITE (ADR-010). Para o uso comum ficar fluido, existe uma lista de domínios de confiança em tools.open_url.trusted_domains (config.yaml, no servidor): URLs cujo domínio (ou subdomínio) está na lista abrem sem perguntar. A lista inicial é youtube.com e music.youtube.com [a confirmar]. Para isso, a Tool ganha um gancho de confirmação dinâmica (requires_confirmation(**args) -> bool, padrão: segue o tier), implementado na T-079. Só tools WRITE podem dispensar a confirmação (regra existente da T-062); a lista de domínios não pode dispensar a política de URL acima.

7. Resultado e erros

Resposta de sucesso: {"type":"result","call_id":"k-9","success":true,"output":"Abri https://www.youtube.com no navegador.","metadata":{"url":"https://www.youtube.com"}}.

  • Executor offline: o brain devolve ToolResult(success=False) com uma mensagem amigável, sem erro técnico (e o erro tipado executor_unavailable do ADR-012 só aparece em comandos que exigem o executor para existir).
  • Timeout: timeout_ms padrão de 10 s para open_url. Se passar, o brain desiste; um result que chegar depois é ignorado e registrado no log.
  • Idempotência: o call_id é único; o executor guarda os últimos call_id por 60 s e não repete um invoke já cumprido que reapareça (reenvio depois de reconexão) [a confirmar].

8. Registro e auditoria

  • O brain registra cada invoke e result no eventlog (nome da tool, tier, dispositivo, sucesso, duração; argumentos com segredos mascarados), como as demais tools.
  • O cliente registra localmente o que abriu e o que recusou (e o desktop mostra "abri youtube.com" no app, ADR-015), para o usuário ver o que foi feito pelo seu computador.

9. O CLI como executor

No modo server, o CLI registra, enquanto estiver conectado, as tools que dependem da máquina local: git_search (READ) e git_deploy (DESTRUCTIVE), com os mesmos schemas e tiers de hoje (T-026). Ao receber invoke, revalida (schema e as validações já existentes: só dígitos nos ids, repositório git, árvore limpa) e chama o código existente de brain/tools/juniper_cmds.py. A confirmação do git_deploy continua sendo a conversa. Sem o CLI conectado, as tools não existem para o cérebro. O repositório é o diretório atual do CLI (sem parâmetro para outro, de propósito).

10. Evolução: media_play e outras tools

Não decidido aqui; as opções para "tocar uma música" são:

  1. O cérebro acha a URL direta da faixa (precisa de uma tool de busca) e o cliente só abre o link. Simples; o autoplay não é garantido.
  2. O cliente abre a página de busca e o usuário clica em tocar.
  3. O Electron carrega o serviço numa janela própria que ele controla por script. Mais confiável que controlar um navegador externo; mais trabalho.

Cada tool nova de executor passa por: schema, tier, política de revalidação, ADR curto e testes nos dois lados.

Consequências

Positivas

  • O cérebro continua sem conhecer o dispositivo; o cliente decide como cumprir.
  • Defesa em duas camadas: o cérebro valida e o cliente revalida, então um brain comprometido (ou um LLM induzido) não executa nada fora do que o cliente declarou.
  • A confirmação reaproveita o mecanismo existente (conversa), sem botões no cliente.
  • O mesmo contrato serve o Electron e o CLI.

Negativas

  • Duas implementações da política de URL (Python no brain, TypeScript no cliente) que precisam ficar iguais; testes nos dois lados e um conjunto de casos compartilhado ajudam.
  • open_url precisa de um gancho novo na Tool (confirmação dinâmica) e de configuração (trusted_domains).
  • Sem resolução de DNS, endereços privados escondidos atrás de um nome público passam pela política.
  • A lista de domínios de confiança é uma conveniência que precisa de cuidado: um domínio de confiança comprometido abre sem perguntar.

Alternativas consideradas

  1. Executor como daemon Python separado. Reaproveitaria o código das tools, mas são duas peças para instalar e manter no PC. Descartada: o desktop já é o app que o usuário abre.
  2. O cérebro manda scripts ou comandos de shell. Descartada: dá a um LLM (ou a conteúdo que o induza) controle total do computador.
  3. Confirmação no cliente (botão "permitir"). Duplicaria o mecanismo do ADR-010 e não funcionaria por voz.
  4. Sem lista de domínios: sempre perguntar. Seguro, mas "abre o YouTube" pediria permissão toda vez.
  5. Tier READ para open_url. Descartada: abrir uma URL pode ter efeito (um link com ação) e o padrão do ADR-006 para o que não é só leitura é WRITE.
