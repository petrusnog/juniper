T-014 — Streaming

Implementa stream() nos dois providers: a resposta chega em pedaços, à medida que o modelo escreve, em vez de aparecer inteira no fim. Arquivos: brain/llm/ollama_provider.py e brain/llm/groq_provider.py.

1. O que ele faz

O contrato da T-011 já previa stream() devolvendo um AsyncIterator[StreamChunk]. Agora ele funciona: cada pedaço de texto sai como um chunk com delta, e o último chunk traz o que só se sabe no fim.

chunkdelta="Olá, "
→
chunkdelta="tudo "
→
chunkdelta="bem?"
→
chunk finaltool_calls · usage · finish_reason

Regra de ouro: juntar todos os delta dá o mesmo texto que chat() devolveria. Os testes verificam isso.

2. Uso

Exemplo

p = GroqProvider()
async for c in p.stream([Message("user", "oi")]):
    print(c.delta, end="", flush=True)
    if c.finish_reason:        # chunk final
        print(c.usage, c.tool_calls)

O que cada chunk traz

  • Intermediários: só delta (texto novo)
  • Final: delta="", tool_calls completas, usage e finish_reason

stream() é um gerador assíncrono: nada acontece até você começar a iterar, e os erros (seção 5) são lançados durante a iteração, não na chamada.

Montando tool calls fragmentadas (Groq)

A Groq manda uma chamada de ferramenta aos poucos. O id e o name vêm no primeiro fragmento; os arguments (uma string JSON) vêm em pedaços que precisam ser concatenados. Várias chamadas podem se intercalar, separadas por index.

fragmento 1: index=0  id="c1" name="open_app" args=""
fragmento 2: index=0                          args='{"target"'
fragmento 3: index=1  id="c2" name="get_time" args="{}"
fragmento 4: index=0                          args=': "firefox"}'
        ↓ no fim, json.loads em cada uma
ToolCall(c1, open_app, {"target": "firefox"})   ToolCall(c2, get_time, {})

Só no fim, com a string completa, o JSON é interpretado. Se estiver inválido, é LLMError (igual ao chat()). A função de montagem é a mesma do chat() (_build_tool_call), então as duas rotas se comportam igual.

4. Por que tool calls só no chunk final?

Uma ferramenta pela metade não serve para nada: o agente (T-030) só consegue executá-la inteira. Por isso os dois providers entregam as chamadas completas e juntas no último chunk, mesmo que o Ollama as envie antes. O texto continua fluindo normalmente enquanto isso.

5. Erros

Mesma tabela do chat(). A diferença é quando aparecem: podem estourar no meio da resposta, depois de você já ter recebido parte do texto.

falha ao abrir (conexão, 401, 429, 5xx…)Antes do primeiro chunk. O router poderá trocar de provider sem o usuário ver nada.mesmos tipos do chat()
falha no meio do streamConexão cai ou estoura o timeout depois de alguns chunks. O texto parcial já foi entregue.LLMUnavailableError / LLMTimeoutError
stream termina sem sinal de fimSem done:true (Ollama) ou sem finish_reason (Groq): resposta truncada.LLMUnavailableError
erro dentro do streamLinha {"error": …} (Ollama) ou x_groq.error (Groq).LLMError
linha que não é JSON / tool sem nome / argumentos inválidosResposta fora do esperado.LLMError

As garantias da T-013 valem aqui também: a chave da Groq nunca aparece nas mensagens, e a chave ausente vira LLMAuthError.

6. Decisões proativas (tomadas sem consultar você)

A spec da T-014 era curta. Estas foram as escolhas que fiz; cada uma é fácil de reverter.

#DecisãoPor quê
1Stream cortado vira LLMUnavailableError (sem done/finish_reason).Entregar uma resposta pela metade como se fosse completa seria pior que um erro. É o mesmo tipo de "provider falhou" que o router já trata.
2Não envio stream_options à Groq.O SDK instalado (1.7.0) não tem esse parâmetro. O uso de tokens vem em x_groq.usage, e o código aceita também usage no topo, caso a API mude.
3Tool calls (inclusive as do Ollama) saem só no chunk final.Contrato uniforme para os dois providers, como a spec pedia. O consumidor não precisa saber qual provider respondeu.
4Chunks intermediários não trazem usage nem finish_reason.Esses campos só existem de verdade no fim; assim "chunk com finish_reason" identifica o último sem ambiguidade.
5Refatoração mínima no chat(): o corpo do pedido e o tratamento de status HTTP passaram para funções compartilhadas (_payload/_status_error no Ollama, _request_kwargs/_build_tool_call na Groq).Evita duplicar a lógica entre chat() e stream(). O comportamento do chat() não mudou, e os testes antigos continuam passando.
6Sem retry de stream.Retomar um stream no meio duplicaria texto. Falha no meio é erro; o router (T-015) decide o que fazer.
7Atualizei as páginas T-012 e T-013 onde diziam que stream() lançava NotImplementedError.Para a documentação não ficar contraditória.

7. Como testar

Automatizado (sem rede)

pytest tests/test_ollama_provider.py \
       tests/test_groq_provider.py -v
Ollama: httpx.MockTransport devolvendo NDJSON, inclusive uma conexão que cai no meio. Groq: stream falso com fragmentos de tool call. Cada um verifica a regra "deltas == chat()".

Manual (Ollama real)

python - <<'EOF'
import asyncio
from brain.llm.ollama_provider import OllamaProvider
from brain.llm.types import Message
async def main():
    p = OllamaProvider()
    async for c in p.stream([Message("user", "conte até 5")]):
        print(c.delta, end="", flush=True)
    await p.aclose()
asyncio.run(main())
EOF
Não executado nesta task: o ambiente de desenvolvimento não tem Ollama nem acesso à Groq.

8. Limitações conhecidas

Sem teste contra servidor real. O formato do NDJSON do Ollama e dos chunks da Groq foi reproduzido a partir da documentação e do SDK; falta confirmar com uma chamada de verdade (principalmente onde a Groq coloca o usage no stream).

Tool calls só no fim: não dá para mostrar "executando ferramenta…" enquanto o modelo ainda decide os argumentos.

Parar no meio: se o consumidor interromper a iteração, a conexão é fechada, mas ainda não há um mecanismo de cancelamento explícito (Ctrl+C amigável fica para o cliente, T-040).

Sem failover ainda: trocar de provider antes do primeiro chunk é trabalho da T-015.
