T-055 — VectorStore

Onde as memórias de longo prazo moram e como são achadas por significado. As memórias ficam na collection memories do MongoDB e a busca compara o vetor da pergunta com os vetores guardados (similaridade de cosseno). Arquivos: brain/memory/vector.py (interface e cálculo) e brain/memory/mongo.py (MongoVectorStore). Decisões de fundo no ADR-011.

1. Como funciona

PeçaO que faz
MemoryUma memória: texto curto, type (preference, project ou fact), status, vetor e o modelo que o gerou. É validada antes de gravar.
VectorStoreA interface: add, get, search, update e delete. O resto da Juniper só conhece ela, então dá para trocar pelo Atlas Vector Search sem mexer em mais nada.
MongoVectorStoreCarrega do banco os vetores das memórias active feitas pelo modelo atual e calcula o cosseno em Python (numpy). Para centenas ou poucos milhares de memórias isso leva milissegundos e não exige Atlas.
searchDevolve as top_k mais próximas com similaridade ≥ threshold, a melhor primeiro, cada uma com sua nota (score, de -1 a 1).

2. Regras que a busca respeita

Só enxerga memórias active. Uma memória superseded (substituída por outra) fica no banco só para auditoria e nunca aparece, nem com filtro.

Só compara vetores do mesmo modelo. Memórias de outro modelo de embeddings são ignoradas (não são comparáveis) até o juniper memory reindex da T-054 atualizá-las. Vetores de tamanho diferente também são pulados.

Filtros são uma lista fechada: type, source.kind e source.session_id, com valor simples. Qualquer outra chave ou operador do MongoDB é recusado.

Documento corrompido é ignorado na busca: um registro ruim não esconde os bons.

update não mexe em _id nem em created_at e atualiza updated_at sozinho. Trocar o vetor exige informar também o embedding_model. delete apaga de verdade, como pede o forget.

3. O que fica no banco

{
  "_id": "mem_20261014033000a1b2c3",
  "text": "O projeto X usa Laravel 11.",
  "type": "project",
  "status": "active",
  "superseded_by": null,
  "embedding": [0.012, -0.087, ...],      // 384 números
  "embedding_model": "intfloat/multilingual-e5-small",
  "source": { "kind": "extracted", "session_id": "..." },
  "created_at": "...", "updated_at": "..."
}

Índices criados na primeira gravação ou busca: (status, type) e created_at. O vetor não tem índice no MVP.

4. Configuração

memory:
  retrieval:
    top_k: 5          # no máximo quantas memórias uma busca devolve
    threshold: 0.0    # similaridade mínima (cosseno); 0.0 = sem corte

Ambos podem ser passados direto em search(...); sem isso valem os da configuração.

5. Limitações conhecidas

O threshold ainda não foi calibrado. O padrão 0.0 não filtra nada. O valor certo depende do modelo e de exemplos reais em PT-BR, e é definido na T-057 (recuperação).

Nada grava memórias ainda. Esta task entrega o armazenamento e a busca; quem decide o que vira memória é a extração (T-056), e as tools remember/recall/forget vêm na T-058.

Carrega todos os vetores ativos a cada busca. É de sobra para o volume pessoal previsto; se chegar a centenas de milhares, a troca é o Atlas Vector Search atrás da mesma interface.

6. Como testar

pytest -m "not integration"   # CI: collection falsa, sem banco
pytest -m integration         # contra o MongoDB local (docker compose up -d)
