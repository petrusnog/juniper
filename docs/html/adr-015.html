Contexto

O destino da Juniper é um cliente desktop que fala com o cérebro remoto e replica o que o CLI faz hoje, com uma interface gráfica e, depois, voz (Sprint 4). O ADR-007 já definia o cliente como fino: captura entrada, exibe saída, nunca executa lógica de agente e nunca acessa o MongoDB. O ADR-012 definiu o protocolo e o ADR-014, o executor.

Este ADR fixa a base técnica do app antes de qualquer linha de código: stack, estrutura, segurança do app, guarda do token, conexão, testes, CI e empacotamento. A Sprint 3 entrega só o chat por texto e o executor com open_url; voz, atalhos globais e bandeja ficam para a Sprint 4.

Decisão

1. Stack

  • Electron + TypeScript. O usuário domina JavaScript, o ecossistema é grande e o executor precisa de acesso ao sistema (abrir o navegador, cofre de credenciais), que o Electron dá.
  • Interface do renderer: React com Vite (via electron-vite) [a confirmar]: é o caminho mais documentado e o chat com stream cabe bem em estado reativo. Uma alternativa mais enxuta (TypeScript puro com Web Components) é possível se a interface ficar simples.
  • WebSocket no processo principal: biblioteca ws. Validação dos argumentos do executor: ajv (JSON Schema). Tipos do protocolo: gerados do JSON Schema da T-074 (seção 7).
  • Idioma: interface em PT-BR; código, comentários e logs em inglês (ADR-001).
  • Alternativas descartadas: Tauri (leve, mas exige Rust para o lado nativo), Qt/Python (não é a linguagem que o usuário domina e o executor ficaria em Python), PWA (não abre o navegador nem guarda credenciais com segurança no sistema).

2. Estrutura

Monorepo: o app fica em desktop/ na raiz do repositório.

desktop/
├── package.json, tsconfig.json, electron-vite.config.ts, eslint.config.js
├── src/
│   ├── main/       processo principal: janela, conexão WebSocket, executor, cofre do token
│   ├── preload/    a ponte mínima (contextBridge) entre main e renderer
│   ├── renderer/   a interface (React)
│   └── shared/     tipos do protocolo (gerados), constantes, política de URL
├── tests/          testes (vitest)
└── README.md       como rodar, testar e empacotar

O código do executor (ADR-014) vive em src/main/executor/, separado da interface. O renderer não toca no WebSocket, no token nem no sistema.

3. Segurança do app

Regras fixas (o app mostra texto vindo de um LLM, então o renderer é tratado como não confiável):

  • contextIsolation: true, nodeIntegration: false, sandbox: true no renderer; o módulo remote não é usado.
  • CSP restritiva (default-src 'self'; sem unsafe-eval; sem origens remotas). Nenhum conteúdo remoto é carregado na janela principal.
  • Navegação bloqueada: will-navigate e setWindowOpenHandler negam tudo; links nas respostas não abrem sozinhos. Um clique num link passa por shell.openExternal só depois da mesma política de URL do open_url (ADR-014).
  • Respostas da IA como texto: o renderer nunca usa innerHTML com conteúdo do LLM. Se houver formatação (Markdown), ela passa por um renderizador que sanitiza o HTML.
  • API da ponte mínima, sempre com validação de entrada no main: connection.getState(), chat.send(text), chat.cancel(), session.list()/resume()/new(), onEvent(callback), settings.get()/set(). Nada de acesso genérico ao sistema de arquivos ou ao Node.
  • Instância única (app.requestSingleInstanceLock()).
  • Dependências fixadas por lockfile (npm ci); atualização de segurança do Electron acompanhada.

4. Token e configurações

  • O token do ADR-007 é guardado com safeStorage do Electron (o cofre do sistema: DPAPI no Windows, Keychain no macOS, o chaveiro do desktop no Linux), em app.getPath('userData'), cifrado; nunca em texto puro, nunca no renderer, nunca em log.
  • Se safeStorage.isEncryptionAvailable() for falso (Linux sem chaveiro), o app não grava o token: pede de novo a cada execução e avisa por quê [a confirmar].
  • Primeira execução: uma tela pede o endereço do servidor (o nome da VPS na tailnet, ADR-013) e o token, testa a conexão e só então grava.
  • Outras configurações (endereço, nome do dispositivo, tema) ficam num arquivo JSON em userData; nenhum dado de conversa é gravado no cliente: o histórico vem do servidor (session.resume, ADR-012).
  • Pré-requisito do usuário: o Tailscale instalado e logado nessa máquina. Se o servidor não for alcançável, o app mostra essa dica.

5. Conexão

O processo principal é dono da conexão WebSocket e implementa o ADR-012: handshake com token, hello/welcome, heartbeat, reconexão com backoff e jitter, retomada da conversa, tratamento dos códigos de fechamento (4401 e 4426 param e mostram o motivo; 1012 reconecta na hora).

Estados mostrados na interface: conectando, online, offline (reconectando), não autorizado e versão incompatível. Quando offline, o app mostra "Juniper indisponível no momento" e preserva o texto digitado (ADR-012: não há fila offline).

7. Tipos do protocolo e testes

  • Os tipos TypeScript são gerados do JSON Schema versionado em docs/protocol/schema.json (T-074) com um script (npm run gen:protocol). O CI falha se o arquivo gerado estiver desatualizado (regerar e comparar).
  • Testes: vitest (unidade e integração leve), com um servidor WebSocket de teste simulando o brain; o código do executor é testado sem Electron (módulos puros); a política de URL usa o mesmo conjunto de casos do teste Python.
  • Qualidade: eslint, prettier, tsc --noEmit no CI.

8. CI

Um job novo no CI para o app (desktop), em Node LTS: npm ci, geração dos tipos do protocolo e verificação, lint, typecheck, test, e build. O job roda quando desktop/** ou docs/protocol/** muda; o workflow existente (pytest) continua intocado. O branch master só aceita o merge com ambos verdes onde aplicável [a confirmar a configuração das regras de proteção].

9. Empacotamento

  • electron-builder. Alvos iniciais: Windows (NSIS) e Linux (AppImage); macOS fica fora por enquanto [a confirmar].
  • Sem auto-update na Sprint 3: o usuário reinstala manualmente. Sem assinatura de código (o Windows pode mostrar o aviso de editor desconhecido); aceito para uso pessoal.
  • O artefato é gerado por um workflow manual (workflow_dispatch) ou localmente; não faz parte do deploy do brain.

10. Fora de escopo (Sprint 4)

Voz (STT e TTS locais), wake word, bandeja do sistema, atalhos globais, notificações e auto-update.

Consequências

Positivas

  • Um app que o usuário consegue manter na linguagem que domina, com o executor no mesmo processo.
  • A segurança do renderer é tratada desde o início (o app exibe texto de um LLM).
  • O token fica no cofre do sistema, não em arquivo.
  • Tipos gerados do mesmo contrato do servidor evitam divergência de protocolo.

Negativas

  • Peso do Electron (memória e tamanho do instalador) em troca de produtividade.
  • Dois ecossistemas no repositório (Python e Node), com CI e dependências separados.
  • Sem auto-update: manter o app atualizado é manual.
  • Depende do Tailscale instalado na máquina do usuário.

Alternativas consideradas

  1. Tauri. Menor e mais leve, mas o lado nativo é Rust, e o usuário prefere JS.
  2. App em Python (Qt). Reaproveitaria código, mas a interface e o executor ficariam menos naturais para quem domina JavaScript e o empacotamento é mais frágil.
  3. PWA no navegador. Sem executor nativo (abrir o navegador, cofre do sistema) e sem cabeçalho de autenticação no WebSocket.
  4. Guardar o token em arquivo de configuração. Mais simples, mas em texto puro; descartado.
  5. Executor como processo separado. Descartado no ADR-014.
