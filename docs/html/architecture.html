Visão geral da arquitetura guia

As camadas da Juniper, onde cada uma mora no código, as regras que as mantêm simples, os modos de execução e o caminho de uma mensagem.

Visão geral

A Juniper segue a lógica de um assistente sempre disponível: um cérebro (o agente, que pensa, lembra e decide) e vários corpos (os clientes: terminal, bot do Telegram, app Android, painel web). Os clientes são finos: capturam a mensagem e mostram a resposta. Quem decide é o cérebro (ADR-007).

Modos de execução

Mododeployment.modeOnde o cérebro rodaClientes possíveis
LocallocalDentro do processo do comando juniper (Instalação sem Docker).Só o próprio terminal.
ServidorserverNum processo próprio (juniper serve), em geral num contêiner (Servidor WebSocket).CLI remoto, Telegram, app Android, dashboard.

O código do agente é o mesmo nos dois modos; muda só quem o hospeda. Em desenvolvimento e em produção o modo é server (Primeiros passos, Produção).

Uma frase, passo a passo

Exemplo: no app, você escreve "amanhã quero uma ida ao dentista, às 16h".

#O que aconteceOnde
1O app manda chat.send pelo WebSocket.Cliente → protocolo
2O servidor confere que a conversa está livre, abre o turno (chat.started) e entrega o texto ao Agent.Servidor
3O agente monta o pedido: persona, perfil, memórias relevantes, a hora atual, o canal do pedido e a lista de tools.Agente, Memória
4O LLMRouter envia ao primeiro provedor da fila; se ele falhar antes de responder, tenta o próximo.LLM
5O modelo pede create_event com título e horário resolvidos.Tools
6O Dispatcher acha a tool; o precheck consulta o Google Calendar antes de perguntar qualquer coisa.Agenda Google
7Sem conflito, a Juniper pergunta "Posso marcar «Dentista», segunda 16h–17h?"; a pergunta chega como chat.token e o turno termina com chat.end.Confirmação
8O seu "sim" é o próximo chat.send; consent.py o interpreta e o evento é criado.Cérebro
9Tudo vai para o log, a conversa é salva e, em segundo plano, o que vale lembrar vai para a memória de longo prazo.Transversal

Regras que mantêm tudo simples

  1. O cérebro não conhece as interfaces. brain/core/ nunca importa de brain/clients/. Por isso a mesma Juniper serve todos os clientes (ADR-007).
  2. Cliente fino. Nenhum cliente tem lógica de agente nem acesso ao MongoDB; histórico e confirmação pendente vivem no servidor (ADR-012).
  3. Providers são trocáveis. O cérebro fala com um LLMProvider, nunca com um provedor específico (ADR-001, ADR-009).
  4. Tool nova = arquivo novo. Cada capacidade é um plugin que se registra sozinho (Tools, ADR-002).
  5. Perigo exige permissão. Ler é livre; alterar pede um "sim" na conversa; destruir também, com aviso; o proibido nunca executa (Segurança, ADR-006, ADR-010).
  6. Um só ponto de configuração. Tudo vem de brain.config.settings (Configuração, ADR-003).
  7. Falha esperada é resultado tipado, nunca exceção que derruba a conexão ou o servidor.
  8. Shell é interface, Python é cérebro. O shell/ só orquestra os comandos legados; a lógica vive em brain/.
