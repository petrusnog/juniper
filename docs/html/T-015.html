T-015 — LLMRouter

Um provider "de mentira" que esconde vários de verdade: tenta o Groq e, se ele não puder responder, passa para o Ollama sem o resto do código perceber. Arquivo: brain/llm/router.py.

1. O que ele faz

O LLMRouter implementa a mesma interface LLMProvider (chat, stream, health_check). O agente (T-030) fala só com ele e não precisa saber quantos providers existem. A ordem vem de llm.priority no config.yaml.

Agenterouter.chat()
→
Groq1º da prioridade
→
Ollamasó se o Groq falhar

Cada chamada começa pelo primeiro provider. Se ele responde, os outros nem são tocados.

2. Quando troca de provider

LLMUnavailableErrorConexão recusada, erro 5xx.failover
LLMTimeoutErrorO provider não respondeu a tempo.failover
LLMRateLimitErrorLimite de requisições (429), comum no plano gratuito do Groq.failover
LLMAuthErrorChave ausente ou recusada: o provider está inutilizável.failover
qualquer outro LLMErrorRequisição inválida, modelo inexistente (404), resposta malformada. Falharia igual no outro provider.propaga

Toda troca gera um logging.warning ("Failover: groq falhou (…)"). Se todos falham, sai um LLMError cuja mensagem lista a causa de cada provider.

3. Streaming: só troca antes do primeiro chunk

Quando o provider falhaO que o router faz
Antes de qualquer chunkTenta o próximo; o usuário não vê nada de diferente.
Depois de já ter entregue textoRelança o erro. Reenviar a pergunta a outro provider repetiria o começo da resposta.

4. Uso

Exemplo

router = LLMRouter()          # lê llm.priority
async for c in router.stream(msgs):
    print(c.delta, end="")
print(router.last_provider)   # "groq" ou "ollama"
await router.aclose()

Extras

  • last_provider: quem atendeu a última chamada
  • providers: lista (somente leitura)
  • health_check(): True se algum estiver saudável
  • aclose(): fecha todos
  • Construtor aceita uma lista de providers (usado nos testes)

5. Ver na prática

Normal

python scripts/try_groq.py
Mostra a saúde de cada provider e, em cada resposta, quem atendeu: juniper [groq]>.

Simulando o Groq fora do ar

python scripts/try_groq.py --simulate-down
Dá ao Groq uma chave inválida. Precisa do ollama serve rodando. Saída esperada: 
[WARNING] Failover: groq falhou (LLMAuthError: …HTTP 401)
juniper [ollama]> …

6. Decisões proativas

#DecisãoPor quê
1Erros fora da lista de failover são relançados.Um 404 de modelo ou uma resposta malformada é problema de configuração ou de código, e esconder isso atrás do Ollama dificultaria o diagnóstico.
2Erro agregado é um LLMError simples, com as causas na mensagem e a última encadeada em __cause__.É o que a spec pedia; um tipo novo não era necessário.
3Adicionei last_provider e providers (fora da spec).Para o script de teste mostrar quem respondeu. Não afetam a interface.
4health_check consulta todos em paralelo e aceita qualquer um saudável.O router continua utilizável enquanto houver um provider de pé.

7. Limitações conhecidas

Sem memória de falhas. Toda chamada tenta o Groq primeiro. Com o Groq fora do ar, cada pergunta espera o timeout dele (30 s) antes de ir ao Ollama. Um circuit breaker resolveria, mas não estava na spec.

Degradação silenciosa. Com chave inválida o sistema segue funcionando pelo Ollama e o aviso só aparece no log. Fica mais visível quando o logging estruturado (T-031) existir.

O modelo muda no meio da conversa. O histórico é reenviado ao Ollama, que tem estilo e qualidade diferentes, principalmente em tool calling.

Ainda não está ligado ao agente. Só o scripts/try_groq.py usa o router; o agente e a CLI entram nas tasks T-030 e T-040.

Falha no meio do stream não é recuperada: o usuário vê o texto parcial seguido do erro.

8. Como testar

pytest tests/test_llm_router.py -v

Usa providers falsos e roteirizados, sem rede. Cobre: primeiro ok sem tocar no segundo, troca para cada um dos 4 erros, todos falhando (causas agregadas), erro sem failover, troca antes do primeiro chunk, falha no meio do stream sem duplicar saída e health_check. Verificado também manualmente com --simulate-down e Ollama real.
