ADR-002 — Schema de Tools

Status
aceito
Data
2026-09-19
Autor
Equipe Juniper
Contexto do Sprint
Sprint 1 — "Hello Agent"
Relaciona-se com
T-002, T-020, T-021, T-030

Contexto

O Juniper v3 é um agente com tool calling: o LLM decide qual ferramenta chamar e com quais parâmetros, e o core Python executa. Isso exige um formato padronizado para descrever cada tool ao LLM.

Precisamos de um formato que:

  • Seja entendido nativamente tanto por Groq quanto por Ollama.
  • Seja extensível (novas tools sem tocar no core).
  • Possa ser gerado automaticamente a partir de código Python.
  • Não exija reescrita se futuramente adicionarmos outros providers.

Decisão

Adotamos o schema OpenAI Function Calling, literalmente. É o formato nativo do Groq, e o Ollama suporta o mesmo formato em /api/chat via campo tools. Também é o padrão de facto do ecossistema.

Formato canônico

{
  "type": "function",
  "function": {
    "name": "open_app",
    "description": "Abre um aplicativo ou URL no sistema operacional do usuário",
    "parameters": {
      "type": "object",
      "properties": {
        "target": {
          "type": "string",
          "description": "URL ou nome do app. Ex: 'https://music.youtube.com' ou 'firefox'"
        }
      },
      "required": ["target"]
    }
  }
}

Regras de declaração

  1. Cada tool é uma classe Python que herda de brain.tools.base.Tool.
  2. Metadados obrigatórios na classe:
    • name: str — identificador único, snake_case
    • description: str — descrição em PT-BR (o LLM usa isso para decidir)
    • parameters: dict — JSON Schema dos parâmetros
    • tier: Tier — nível de segurança (ver ADR-006)
  3. Método run(**kwargs) -> ToolResult — implementação real.
  4. Descrição importa. O LLM decide com base na description. Descrições vagas resultam em uso errado. Cada tool deve descrever o que faz e quando usar.

Geração automática

O brain.tools.registry coleta todas as classes registradas (via decorator @register_tool) e gera a lista de schemas para passar ao LLM. Nenhuma tool precisa se registrar manualmente numa lista central.

ToolResult

Retorno padronizado de toda tool:

@dataclass
class ToolResult:
    success: bool
    output: str | None = None
    error: str | None = None
    metadata: dict | None = None

Isso permite que o agent loop (T-030) trate sucesso e falha de forma uniforme, e registre tudo no log estruturado.

Consequências

Positivas

  • Compatibilidade nativa com Groq e Ollama sem adaptação.
  • Adoção futura de OpenAI, Anthropic (com conversão) ou outros é trivial.
  • Auto-descoberta mantém o core enxuto e a adição de tools barata.
  • Schema é auto-documentado — serve tanto pro LLM quanto pra humanos.

Negativas

  • JSON Schema é verboso. Tools complexas geram schemas longos que consomem tokens de contexto. Mitigação: manter parâmetros enxutos.
  • Se algum provider futuro não suportar Function Calling no formato OpenAI, precisaremos de uma camada de tradução (fora do escopo do Sprint 1).

Alternativas consideradas

  1. Formato próprio (ad-hoc). Rejeitada: reinventar a roda, perder compatibilidade com providers, obrigar tradução.
  2. Anthropic Tool Use format. Rejeitada: Groq e Ollama não suportam nativamente; obrigaria tradução para os providers principais.
  3. DSL declarativa em YAML para definir tools. Rejeitada: as tools precisam de lógica Python real (subprocess, HTTP, etc.). YAML só descreveria metadados, adicionando camada sem benefício.
  4. Registrar tools manualmente numa lista. Rejeitada: propenso a erro humano, dificulta adicionar tools.
