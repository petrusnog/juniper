ADR-038 — Kanbai: orquestrador de agentes em kanban

Status

Contexto

O desenvolvimento da Juniper segue tasks pequenas e verificadas (Como contribuir). O Petrus quer que agentes de IA movam essas tasks por uma esteira visível, num quadro estilo Trello, e que ele só entre na revisão final. O produto se chama Kanbai e roda localmente, num container Docker, fora da Juniper: é um projeto à parte, em repositório próprio, que trabalha sobre o repositório da Juniper.

A base de conhecimento (ADR-037) existe para que as agentes consultem a documentação por notas, sem ler documentos extensos.

O pedido, na íntegra

O texto abaixo é o pedido original do Petrus, sem edição. É a fonte da verdade do que o Kanbai deve ser. As seções seguintes apenas organizam e apontam as lacunas.

Vamos desenvolver um orquestrador de agentes para atuar nas tarefas da Juniper. Kanbai será uma plataforma de tarefas em formato kanban inspirado no trello, só que com a diferença que as tarefas serão movimentadas por agentes de IA. Essa plataforma irá rodar em um container docker no meu ambiente local, e deve entregar uma interface inspirada em cards do trello com temática anime, faça uso de desenhos de garotas mangá, monte fuji, pétalas de cerejeira caindo no background, deve ser um visual bem engraçado mas sem muita poluição visual. Os agentes de IA devem se conectar ao serviço local via MCP, e a arquitetura deve ser agnóstica quanto a modelos, ou seja, deve ser compatível com claude e codex. Cada agente deve ser uma garota de anime aleatória obtida da Nekos API https://nekosapi.com/docs, tente filtrar a imagem por tag de personagem feminina e dê um nome aleatório para as agentes e o cargo delas será o tipo de agente que ela é (executora, revisora).

Antes de seguirmos com a criação da Juniper, vamos otimizar o RAG do projeto Juniper, atualmente a documentação da Juniper está localizada em docs, e é uma série de MDs puros, gostaria que evoluíssemos para uma base de dados relacional em postgresql com recurso de busca vetorial que os agentes do orquestrador pudessem consultar otimizando custo de tokens, não precisar ler documentos extensos para adquirir uma informação pontual, basta obter o conhecimento útil por nota, envolva todos os mds dentro de docs nessa nova versão de memória.

Segue a esteira que os agentes irão seguir, cada coluna, e onde cada agente irá entrar:

Backlog: Status inicial de todas as tarefas. A agente delegadora será responsável por analisar as tarefas do backlog, e a partir de uma busca vetorial pelo RAG e análise do código atual, criam uma branch (Referente a branch do Github da Juniper, ex: feature/T256, feature/T123, etc, uma branch por tarefa) refinam a tarefa em uma série de KAI's, KAI é um card, uma unidade de trabalho que se converterá em um commit na branch da tarefa no projeto no final do fluxo. Cada KAI contém título, descrição (LONGTEXT), story points (grau de complexidade), e task associada (para onde vai o commit). A agente irá obter a tarefa do backlog e criar KAI's na coluna a fazer. Essas KAI's estarão vinculadas as tarefas.

A fazer: A agente delegadora irá cadastrar os KAI's recém criados nessa coluna, para que uma agente executora possa iniciar o seu desenvolvimento de acordo com as diretrizes do KAI, todo KAI deve conter um grau de complexidade medido por story points, e instruções claras e objetivas do que deve ser desenvolvido. De acordo com o grau de story points, o modelo do agente será escolhido, tasks mais simples vão gerar agentes executores que rodam em modelos mais baratos, tasks mais complexas, agentes que rodam em modelos mais sofisticados. Quando uma agente executora iniciar um desenvolvimento, ela colocará o card em Fazendo (IA).

Fazendo (IA): Uma vez em Fazendo (IA), a task está oficialmente em desenvolvimento, podem haver no máximo 3 agentes executoras rodando em paralelo nessa V1, posteriormente vamos desenvolver uma forma mais sofisticada de controlar o numero de agentes. Ao fim do desenvolvimento, a agente executora irá emitir um relatório no comentário do KAI, e mover o KAI para Revisando (IA).

Revisando (IA): Uma vez nessa coluna, uma agente QA irá analisar o código desenvolvido pela agente executora, esse agente deve analisar o código apenas com o contexto da arquitetura da task e dos critérios de aceite da task, não deve ter o contexto enviesado da agente executora, o papel dessa QA é validar se todos os critérios de aceite estão sendo contemplados através de code review, escrita de testes unitários, e demais meios de validação. Vale ressaltar que agentes QA devem rodar em modelos sofisticados como Opus do Claude. Após a revisão, se houverem falhas, o KAI será movido para coluna correção, e o agente executor responsável pelo KAI entra em ação novamente com todo o contexto que adquiriu do desenvolvimento, e trabalha nas correções da agente QA, uma agente executora só morre quando o seu KAI for aprovado pela validação humana. Após o ciclo de validação finalizar, o kai vai para revisão humana.

Revisão Humana: Os KAI da tarefa irão ser enviados para revisão humana com um resumo simples e objetivo do que foi desenvolvido, o intuito é tentar sintetizar a complexidade para revisão humana, destacando os pontos cruciais e uma visão macro do que foi desenvolvido. Após a validação humana, eu posso mover a tarefa para correção ou para feito. Se for para correção, mesmo fluxo de correção apresentando anteriormente, se for para feito, o commit é feito na branch.

Correção: Correções que serão analisadas e corrigidas pela agente executora responsável pelo KAI.

Feito: Commit do KAI entra na branch seguindo o git-flow feature(id-task): o que foi feito no kai. Quando todos os KAI escopados para aquela task forem concluídos, integrar com github e gerar o PR da branch da tarefa para master sem fazer o merge.

Requisitos transversais

  1. Local e em container. O Kanbai roda num container Docker na máquina do Petrus; nenhuma porta pública (ADR-013): só 127.0.0.1.
  2. Agentes por MCP. As agentes se conectam ao serviço local via MCP; o Kanbai expõe as tools do quadro (listar, mover, comentar, criar KAI...). A arquitetura é agnóstica de modelo: o mesmo servidor atende Claude e Codex (e qualquer cliente MCP).
  3. Agentes são garotas de anime. Cada agente nasce com uma imagem obtida da Nekos API (https://nekosapi.com/docs), filtrando, na medida do possível, pela tag de personagem feminina; um nome aleatório; e o cargo é o tipo dela (executora, revisora/QA, delegadora). Se a API estiver fora, usar uma imagem local de reserva, nunca falhar a criação da agente.
  4. Interface. Cards no estilo do Trello com tema anime: desenhos de garotas mangá, monte Fuji e pétalas de cerejeira caindo no fundo. Visual engraçado, mas sem poluição visual (as pétalas são sutis; o quadro continua legível).
  5. Revisão independente. A QA nunca recebe o raciocínio nem o histórico da executora; recebe a arquitetura, os critérios de aceite e o diff.
  6. Usa a base de conhecimento. A delegadora (e as demais) consultam a documentação da Juniper pelo MCP da ADR-037 (search_notes, get_note, neighbors), em vez de ler docs/ inteiro.

Modelo de dados mínimo

  • Tarefa: id (T256), título, descrição, critérios de aceite, branch, coluna (Backlog até o PR aberto), link do PR.
  • KAI: id, tarefa, título, descrição (texto longo), story points, coluna, executora responsável, comentários (o relatório da executora, o parecer da QA, o resumo humano), hash do commit quando Feito.
  • Agente: id, nome, cargo, URL da imagem (guardada), modelo/provedor em uso, estado (ociosa, trabalhando, encerrada), KAI atual.
  • Evento: toda movimentação (quem, de onde, para onde, quando), para o histórico do quadro.

Consequências

  • Positivas: a esteira inteira fica visível; revisão independente por construção; custo de modelo proporcional à complexidade; o humano revisa um resumo, não o fluxo todo.
  • Negativas: orquestrar agentes paralelos em branches e worktrees traz conflitos de merge entre KAIs da mesma tarefa (a delegadora deve ordenar e escopar KAIs para minimizar isso); custo e tempo de QA em modelo sofisticado em todo KAI.
  • Riscos: agente com acesso ao repositório e ao git (ADR-006): o Kanbai deve rodar cada agente numa worktree isolada, sem permitir push em master nem merge (o PR é aberto, nunca mergeado).

Fases propostas

  1. Backend: modelo de dados, colunas, regras de movimentação (incluindo o limite de 3 executoras e quem pode mover o quê) e testes.
  2. Servidor MCP do quadro: tools para as agentes, testado com Claude e com Codex.
  3. Interface: quadro anime, agentes com imagem da Nekos API, nome aleatório e cargo.
  4. Agentes: delegadora, executora (com escolha de modelo por story points), QA isolada, e a integração com Git/GitHub (branch, commit por KAI, PR sem merge).

Alternativas consideradas

  • Usar o Trello/GitHub Projects com automações: descartado; o pedido é uma plataforma própria, movimentada por agentes via MCP e com visual próprio.
  • Um único agente que faz tudo: descartado; a revisão precisa ser independente da execução, e o modelo precisa variar com a complexidade.
