ADR-001 — Idioma, Providers de LLM e Camada HMI

Status
aceito

Contexto do Sprint

Relaciona-se com

Contexto

O Juniper v2 usava commands/chat.sh para conversar com o Ollama via curl + jq. Essa abordagem é stateless, frágil para streaming de tokens, e não suporta tool calling — que é o pilar da v3.

A v3 precisa de:

  1. Suporte a múltiplos providers de LLM com failover.
  2. Streaming de tokens de forma estável.
  3. Tool calling nativo (Function Calling).
  4. Uma camada HMI que continue sendo "comando de terminal nativo".

Além disso, a persona da Juniper (sarcástica, técnica, vibrante) precisa ser preservada, e o idioma de interação com o usuário precisa ser definido.

Decisão

1. Idioma

  • Interação com o usuário e persona: Português Brasileiro (PT-BR).
  • Código-fonte: Nomes de variáveis, funções, classes, comentários e logs estruturados em inglês. Isso garante consistência técnica e facilita integração futura com bibliotecas e padrões do ecossistema Python.
  • Mensagens de erro para o usuário final: PT-BR, com a persona da Juniper injetada.

2. Providers de LLM

  • Groq (groq-sdk): Provider primário. Latência ultra-baixa via LPU, tool calling excelente, tier gratuito generoso.
  • Ollama (HTTP /api/chat): Provider secundário / fallback. Roda localmente na GPU do usuário (RX 590, 8GB VRAM), suporta os mesmos schemas de tool calling.
  • Configuração: A prioridade é configurável via config.yaml (llm.priority). O comportamento padrão é [groq, ollama] — tenta Groq, cai para Ollama em erro de rede, timeout, ou ausência de API key.
  • Modelo default do Groq: llama-3.3-70b-versatile (tool calling confiável, contexto amplo).
  • Modelo default do Ollama: llama3.1 (já calibrado no v2 para 8GB VRAM).

3. Camada HMI

  • O commands/chat.sh é removido na v3. Toda interação conversacional passa por python -m brain chat (invocado via wrapper fino em shell/juniper.sh).
  • O shell/juniper.sh continua sendo o ponto de entrada do usuário no terminal — mas deixa de conter lógica de negócio. Ele apenas roteia para o core Python.
  • Comandos legados (gitgrep, deployfeature) são preservados em shell/commands/ e migrarão para tools do agente no Sprint 2.

Consequências

Positivas

  • Um único caminho de chat elimina ambiguidade de manutenção.
  • Failover automático entre Groq e Ollama aumenta robustez.
  • Separação clara entre interface (shell) e inteligência (Python) viabiliza tool calling, streaming e memória.
  • Persona versionada em prompts/juniper.md permite evolução controlada.

Negativas

  • O Groq exige internet e API key. O usuário precisa configurar GROQ_API_KEY no .env (embora o sistema funcione só com Ollama, se preferir).
  • O Ollama exige daemon rodando. O scripts/dev.sh avisa mas não instala.
  • Duplicação de manutenção de schemas de tool calling entre os dois providers (mitigado pelo schema único em ADR-002).

Alternativas Consideradas

  1. Só Ollama, sem Groq.
    • Rejeitada: Latência alta prejudica a UX de agente interativo, e o tool calling de modelos 8B é menos confiável.
  2. Só Groq, sem Ollama.
    • Rejeitada: Sem fallback offline, o usuário perde soberania sobre dados sensíveis.
  3. Manter chat.sh em paralelo ao novo brain.
    • Rejeitada: Dívida técnica imediata, dois caminhos de manutenção, confusão de comportamento.
  4. Internacionalização (i18n) desde o início.
    • Rejeitada por YAGNI. A persona vive em PT-BR; adicionar i18n agora é complexidade sem uso.
