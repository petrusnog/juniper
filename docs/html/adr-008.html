ADR-008 — Integração com Google Calendar (primeira tool real)

Contexto

A primeira tool real da Juniper deixa de ser open_app e passa a ser a integração com o Google Calendar: marcar compromissos por conversa (ex.: "amanhã às 16h, dentista"), avisando quando já houver algo no horário.

Dois problemas práticos apareceram ao planejar:

  1. Autenticação. O fluxo OAuth de usuário exige publicar o app na tela de consentimento do Google (campo de domínio obrigatório; o localhost é recusado). Em modo "Testing", o token expira em 7 dias. Além disso, o OAuth precisa de navegador, o que não existe na VPS do Sprint 2.
  2. Data e hora. O LLM não sabe que dia é hoje. Sem isso, "amanhã" e "sexta" viram datas erradas.

Decisão

1. Autenticação por conta de serviço

  • Uma conta de serviço do Google Cloud acessa a Calendar API; o usuário compartilha os calendários com o e-mail dela (como se fosse uma pessoa).
  • Chave JSON em ~/.juniper/certs/gcp-key.json, permissão 600, no .gitignore, nunca logada.
  • Sem tela de consentimento, sem token que expira, sem navegador: funciona igual local e na VPS.
  • Escopo: https://www.googleapis.com/auth/calendar.events.

2. Calendários

CalendárioPermissão dada à conta de serviçoUso
Juniper (novo, na conta Gmail pessoal)Fazer alterações em eventosOnde a Juniper cria e apaga eventos
PrincipalVer todos os detalhes do evento [a confirmar]Só leitura, para detectar conflitos
  • O ID do calendário Juniper fica em config.yaml (google.calendar_id).
  • Eventos aparecem no celular normalmente (app Google Agenda sincroniza as agendas da conta).
  • Trava de segurança [a confirmar]: create_event e delete_event só operam no calendário configurado; o calendário principal nunca é alterado.

3. Tools

ToolTierLocalityO que faz
list_eventsREADCLOUDLista compromissos de um intervalo (título e horário; sem descrição/local/convidados)
create_eventWRITECLOUDCria o evento; antes de criar, checa conflitos
delete_eventDESTRUCTIVECLOUDRemove um evento do calendário Juniper

4. Fluxo de conflito (conversacional)

  1. Ordem: o LLM chama create_event direto (sem list_events antes, para poupar chamadas). Um gancho Tool.precheck valida a entrada e procura conflitos antes do [y/N]; assim o usuário nunca confirma algo que vai falhar. O run checa de novo antes de gravar. list_events fica para responder "o que tenho marcado?" e para obter ids.
  2. create_event encontra um evento no horário e não cria: devolve ToolResult(success=False) com o nome, o horário e o id do evento conflitante.
  3. O LLM pergunta ao usuário: "Já existe «Dentista» às 16h. Desmarco para marcar este?"
  4. Se o usuário aceitar, o LLM chama delete_event; o dispatcher ainda pede a confirmação do tier DESTRUCTIVE (dupla segurança). Depois chama create_event de novo.
  5. Se o conflito estiver no calendário principal, a Juniper só avisa (não apaga); a decisão é do usuário.

5. Data e hora

  • Fonte: relógio do sistema + zoneinfo com settings.agent.timezone (America/Sao_Paulo). Sem API externa (uma API de hora adicionaria dependência de rede sem ganho; o relógio da VPS usa NTP).
  • Módulo brain/core/clock.py expõe a hora atual com fuso.
  • O agente injeta no prompt, a cada requisição (não só no início da sessão), algo como: "Agora: domingo, 11/10/2026, 17:30 (America/Sao_Paulo)".
  • Tools recebem datas em ISO 8601 com offset; datas no passado são recusadas.
  • Aviso operacional: no WSL o relógio pode atrasar depois de suspender o PC; sincronizá-lo resolve.

6. Padrões

  • Duração padrão quando não informada: 1 hora [a confirmar].
  • Lembrete padrão dos eventos criados: a definir (sugestão: 30 min antes).
  • Descrição dos eventos criados inclui a assinatura "Agendado pela Juniper".

6b. Economia de tokens (Groq gratuito)

O plano gratuito limita tokens por minuto (≈8k) e cada chamada reenvia o prompt. Decisões: menos chamadas por pedido (item 0 acima); prompt de sistema estável (a hora vai na mensagem do usuário) para permitir cache; llm.groq.reasoning_effort configurável (low para gpt-oss); descrições de tools enxutas; histórico limitado, sem resultados antigos de tools; uso de tokens exibido por chamada.

7. Privacidade

Compromissos lidos viram texto enviado ao LLM (Groq, na nuvem). Por isso list_events devolve o mínimo necessário (título e horário).

8. Identidade da Juniper (adiado)

Com conta de serviço, o criador do evento aparece como o e-mail da conta de serviço (sem nome nem foto). Uma conta Google própria da Juniper (nome + foto como organizadora) fica para depois do deploy em nuvem, quando houver domínio para a tela de consentimento OAuth.

Consequências

Positivas

  • Sem expiração de token e sem passo de navegador; serve também para a VPS.
  • A Juniper não toca na agenda real (escrita só no calendário Juniper).
  • Reaproveita a base de tools, os tiers e a confirmação já decididos.

Negativas

  • A chave da conta de serviço é um segredo de longa duração.
  • Três tools (e não uma) e dependências novas: google-api-python-client e google-auth (bibliotecas síncronas, executadas via asyncio.to_thread).
  • O primeiro teste ponta a ponta depende da configuração manual no Google Cloud.
  • Eventos aparecem com o e-mail da conta de serviço como criador até a conta própria existir.

Alternativas consideradas

  1. OAuth de usuário publicado. Rejeitada por ora: o console exige domínio e a tela de consentimento; volta após o deploy (item 8).
  2. OAuth em modo "Testing". Rejeitada: token expira a cada 7 dias.
  3. Conta Google dedicada à Juniper agora. Adiada: exige OAuth e o mesmo domínio.
  4. API externa de data e hora. Rejeitada: dependência extra sem ganho real.
  5. Manter open_app como primeira tool. Substituída por esta decisão do usuário; open_app continua no backlog.
