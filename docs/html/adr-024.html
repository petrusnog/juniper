ADR-024 — Música (YouTube Data API, playlists e gosto musical)

Contexto

O usuário quer que a Juniper ache e toque músicas no YouTube Music do celular dele, crie playlists personalizadas e aprenda o gosto musical dele. Uma POC com a biblioteca não oficial ytmusicapi autenticou, mas devolveu HTTP 403 em todas as chamadas com um token OAuth de client próprio, e a documentação não traz correção. Já o caminho "achar o videoId pela API oficial e abrir o link no celular" funcionou na POC.

Decisão

1. API oficial, link aberto no celular

  • Achar a faixa: YouTube Data API v3 (search.list, tipo vídeo, categoria de música 10), gratuita, com chave de API (sem login do usuário).
  • Tocar: o LLM chama music_search, escolhe o resultado e chama open_url com o link https://music.youtube.com/watch?v=<videoId>. O domínio music.youtube.com está na lista de confiança (ADR-014), então abre sem perguntar; o celular redireciona para o app do YouTube Music e o módulo de autoplay do app dá o play (ADR-022). Não existe uma tool "tocar" separada: duas tools pequenas compõem melhor e cada uma tem seu tier.
  • A ytmusicapi fica fora do caminho crítico. Pode voltar como extra opcional atrás da mesma interface se um dia valer o esforço (ela daria o histórico de reprodução).

2. Interface MusicProvider

Tudo passa por uma interface (MusicProvider: search, radio_url, list_playlists, create_playlist, add_to_playlist), como os providers de LLM. A implementação inicial é a YouTubeProvider. Falhas viram resultado tipado com metadata.code: quota_exhausted, auth_required, auth_expired, not_configured, not_supported, invalid_request, storage_error, api_error, network_error (regra 8). Nenhuma exceção chega ao LLM com a mensagem crua (pode ter segredos).

3. Busca e ranqueamento

  • Resultados limitados a 5 (parâmetro limit, máximo 5), cada um com video_id, title, artist (nome do canal sem o sufixo " - Topic"), url e kind.
  • Preferência por faixas oficiais: canais "Artista - Topic" (áudio oficial gerado pelo YouTube Music) vêm primeiro; depois o resto, na ordem da API. Títulos com "live", "cover", "karaoke", "reaction" e "remix" que o usuário não pediu descem na lista. A heurística é simples e deterministica; a escolha final é do LLM, que vê os resultados.
  • Rádio ("toca algo parecido"): mode="radio" devolve o link de mix (...&list=RDAMVM<videoId>). Se o YouTube Music monta a fila e dá autoplay a partir dele é a confirmar no aparelho; na dúvida a tool devolve o link de faixa única.
  • Conteúdo vindo da API (títulos, descrições) é dado, nunca instrução (ADR-006), e nunca alimenta opinião, sentimento ou personalidade (ADR-017).

4. Cota

  • A cota padrão é de 10.000 unidades por dia por projeto (zera à meia-noite no horário do Pacífico): busca 100, leitura 1, escrita em playlist 50 [a confirmar na tabela oficial de cotas].
  • O cérebro conta o que gasta em ~/.juniper/music/quota.json (por dia do Pacífico) e recusa de forma tipada (quota_exhausted) ao chegar a music.daily_quota_limit (padrão 9.000, com margem), em vez de levar um 403 do Google. O erro explica quando a cota volta.

5. Playlists (precisam do login do usuário)

  • Criar playlist e adicionar faixas exigem o OAuth do usuário (escopo https://www.googleapis.com/auth/youtube), pelo fluxo de código de dispositivo (juniper music login): o comando mostra um link e um código, o usuário autoriza num navegador e o cérebro guarda o token de renovação em ~/.juniper/music/oauth.json (modo 600, fora do git, montado como arquivo na VPS). O client_id e o client_secret ficam em arquivo ou variável de ambiente (JUNIPER_YOUTUBE_CLIENT_ID, JUNIPER_YOUTUBE_CLIENT_SECRET), nunca em código ou imagem.
  • O token se renova sozinho. Na VPS, o diretório ~/.juniper/music é um volume (não um arquivo montado: o token é gravado por troca de arquivo, que um bind mount de arquivo único impede). Se o app OAuth estiver em modo de teste, pelo que sei o Google expira o token de renovação em 7 dias; quando isso acontecer a tool devolve auth_expired e a Juniper pede para o usuário rodar o login de novo. Publicar o app OAuth (em produção, sem verificação, uso pessoal) evita isso [a confirmar a regra vigente e a escolha do usuário].
  • As playlists aparecem na biblioteca do YouTube Music do usuário.

6. Tools e tiers (ADR-006)

ToolTierLocalityO que faz
music_searchREADCLOUDBusca faixas e devolve links.
music_playlistsREADCLOUDLista as playlists do usuário.
music_playlist_createWRITECLOUDCria uma playlist privada (com confirmação em palavras).
music_playlist_addWRITECLOUDAdiciona faixas a uma playlist (com confirmação).
music_feedbackWRITE (sem confirmar)CLOUDRegistra "gostei", "não gostei" ou "pulei" de uma faixa (item 8).

Cada chamada aceita até 25 faixas (cada faixa adicionada custa 50 unidades de cota; o custo total é reservado antes de criar). Apagar playlist não existe na v1; entraria como DESTRUCTIVE. A music_playlist_create descreve o que vai criar (nome e quantidade de faixas) na pergunta de confirmação; a music_playlist_add confere o id entre as playlists do usuário e usa o nome verdadeiro na pergunta. Uma falha no meio devolve o id e quantas faixas entraram, para completar em vez de duplicar. Playlists são sempre PRIVATE por padrão; mudar isso é uma decisão do usuário.

7. Segredos e configuração

JUNIPER_YOUTUBE_API_KEY no .env (como a chave da Groq); music.enabled (padrão false), music.daily_quota_limit, music.search_limit, music.region (padrão BR), music.oauth_file. Nada de chave em log: a máscara do log de eventos cobre key= e token= em URLs, e a YouTubeProvider nunca coloca a chave em mensagem de erro.

8. Gosto musical (Memória V2)

  • A API oficial não entrega o histórico de reprodução. O gosto vem de três fontes: o que o usuário pede ("toca Djavan"), o feedback que ele dá ("gostei dessa", "pula") e, no futuro, as curtidas lidas pela API.
  • O ADR-017 só deixa o que o usuário escreveu alimentar as camadas subjetivas. Pedidos e feedback são falas dele, então valem; resultados de busca e títulos da API nunca valem.
  • music_feedback grava em uma coleção própria (music_taste: faixa, artista, signal, quando, a citação das palavras dele, sessão), com limites (30 por conversa, 5.000 no total, repetição em 1 minuto vale uma). Como quem chama a tool é o LLM, a regra do ADR-017 depende da instrução da tool; a citação é a trilha de auditoria. A v1 só registra; um comando juniper music taste mostra o que foi guardado, com opção de apagar tudo. Que o sonho noturno leia esses eventos e forme crenças sobre o gosto é um passo seguinte, que muda o ADR-017 e fica fora desta decisão [a confirmar].
  • Para evitar a "bolha", uma dose de exploração (sugerir algo fora do que já foi tocado) fica como instrução de persona na etapa que usar o gosto, não aqui.

Consequências

Positivas

  • Caminho oficial, gratuito e estável; o tocar não depende de login.
  • A interface isola o provider: trocar a implementação não toca a Juniper.
  • Cota e segredos controlados pelo cérebro.

Negativas

  • Sem histórico de reprodução, o gosto cresce mais devagar.
  • A busca por categoria às vezes traz vídeos que não são faixas; o ranqueamento só reduz isso.
  • 100 unidades por busca limitam a uns 90 pedidos por dia.
  • O login OAuth de playlists tem a pegadinha da expiração em modo de teste.
  • O autoplay depende do app e do Android (ADR-022).

Alternativas descartadas

  1. ytmusicapi. Descartada do caminho crítico: 403 na POC, não oficial e frágil.
  2. Tool única play_music. Descartada: mistura leitura com abrir link; duas tools deixam cada tier no lugar.
  3. Spotify. Fora do escopo: o usuário usa o YouTube Music.
  4. Guardar o histórico do YouTube. Não é possível pela API oficial.
