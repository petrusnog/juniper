Contexto

Hoje o brain/clients/cli.py monta o Agent dentro do próprio processo (deployment.mode: local). O ADR-007 decidiu que, em produção, o cérebro roda numa VPS e os clientes falam com ele pela rede, mas detalhou só o protocolo brain ↔ executor (register, invoke, result, heartbeat). Falta definir como um cliente (o CLI remoto e o app Electron) conversa com o cérebro: como entra, como manda texto, como recebe a resposta em stream, como retoma uma conversa, como pede comandos de memória e o que acontece quando a conexão cai.

O ADR-010 simplificou parte do problema: a confirmação de ações perigosas é uma conversa (a Juniper pergunta em palavras e o "sim" vem como a próxima mensagem), então nenhum turno fica bloqueado esperando um clique. O cliente continua fino: entrega texto e mostra texto.

Este ADR fixa o contrato antes do código, para valer igual em Python (servidor e CLI) e em TypeScript (Electron).

Decisão

1. Transporte

  • Um único WebSocket por cliente, carregando chat, sessões, comandos de memória e a parte do executor (decisão da Sprint 3; o custo de infraestrutura é o mesmo de HTTP, a diferença é só de engenharia: reconexão e retomada).
  • Endereço: ws://<host>:<porta>/v1/ws. O prefixo /v1 é a versão do canal; a versão do protocolo vai no handshake (seção 3). Host e porta vêm de deployment.server (ADR-003); o padrão de produção é o nome da VPS na rede Tailscale.
  • Quadros de texto, JSON em UTF-8, uma mensagem por quadro. Quadros binários são recusados.
  • Dentro do Tailscale o tráfego já é cifrado (WireGuard), então ws:// é aceito. Fora da tailnet seria obrigatório wss:// atrás de um proxy; isso está fora do escopo (ADR-013).
  • O servidor também responde GET /health na mesma porta (HTTP, sem autenticação, só informa o estado), usado pelo Docker e pelo deploy (ADR-013).

2. Envelope

Toda mensagem tem type (string) e, quando faz parte de um pedido, id (string única, gerada por quem pede, ex.: UUID). Respostas e eventos ligados a um pedido levam reply_to com o id original.

{ "type": "chat.send", "id": "c-7f3a", "text": "o que tenho amanhã?" }

Campos desconhecidos são ignorados (compatibilidade para frente). Tipos desconhecidos geram um error com code: "bad_request" sem fechar a conexão.

Limites: mensagem de até 1 MiB; texto de chat.send até 32.000 caracteres [a confirmar].

3. Conexão e autenticação

  1. O cliente abre o WebSocket com Authorization: Bearer <token> no handshake HTTP (o mesmo token estático do ADR-007, em deployment.auth.token_file).
  2. Token ausente ou errado: o servidor responde 401 antes do upgrade; se o upgrade já ocorreu, fecha com código 4401. A comparação é em tempo constante e o token nunca aparece em log.
  3. O cliente manda hello; o servidor responde welcome.
{ "type": "hello", "protocol_version": 1,
  "client": { "kind": "desktop", "version": "0.1.0", "device_id": "a1b2c3", "device_name": "Meu PC" },
  "resume": { "session_id": "20261015-101500-ab12cd" } }
{ "type": "welcome", "protocol_version": 1, "server_version": "4.0.0",
  "heartbeat_seconds": 30,
  "session": { "id": "20261015-101500-ab12cd", "resumed": true, "turns": 6 } }
  • client.kind: cli ou desktop (novos tipos entram sem quebrar nada).
  • device_id é estável por instalação; device_name é para o usuário (a Juniper cita o nome quando fala de dispositivos).
  • resume é opcional: {"session_id": "..."} ou {"latest": true} (o --resume do CLI). Sem resume, o servidor abre uma conversa nova.
  • Versão incompatível: o servidor manda error com code: "unsupported_version" e fecha com 4426. Mudanças compatíveis (campos e tipos novos) não aumentam protocol_version; só uma quebra aumenta.
  • Uma segunda conexão com o mesmo device_id substitui a primeira, que é fechada com 4409.

Autenticação no navegador (PWA futuro): a API de WebSocket do navegador não permite cabeçalhos. Quando o PWA existir, o token irá no primeiro quadro (hello.token), aceito só se o cabeçalho faltar [a confirmar; fora da Sprint 3].

4. Heartbeat

  • O servidor manda {"type":"ping"} a cada 30 s; o cliente responde {"type":"pong"}. É heartbeat de aplicação (e não os quadros ping/pong do WebSocket) porque funciona igual em todos os clientes e atravessa proxies.
  • Qualquer quadro recebido conta como sinal de vida. 90 s sem nenhum sinal, em qualquer direção, e quem notou fecha a conexão (4408) e libera os recursos. Isso vale também para o catálogo de tools do executor (ADR-007).

5. Chat

O cliente manda o texto e recebe a resposta em stream. O estado da conversa (histórico, confirmação pendente) vive no servidor.

DireçãoTipoCamposQuando
cliente → servidorchat.sendid, textUma mensagem do usuário.
servidor → clientechat.startedreply_to, turn_id, session_idO turno começou.
servidor → clientechat.tokenturn_id, textUm pedaço da resposta (vem em ordem).
servidor → clientechat.endturn_id, finish, usage?, timing?O turno terminou.
cliente → servidorchat.cancelturn_idInterrompe o turno em andamento.
servidor → clienteerrorreply_to?, code, message, retryableQualquer falha (seção 8).

finish é ok, cancelled, max_iterations (a Juniper parou por excesso de voltas) ou error. timing só vem se agent.show_timing estiver ligado.

{ "type": "chat.started", "reply_to": "c-7f3a", "turn_id": "t-12", "session_id": "20261015-101500-ab12cd" }
{ "type": "chat.token", "turn_id": "t-12", "text": "Amanhã você tem " }
{ "type": "chat.token", "turn_id": "t-12", "text": "o dentista às 16h." }
{ "type": "chat.end", "turn_id": "t-12", "finish": "ok", "usage": { "total_tokens": 1840 } }

Regras:

  • Um turno por vez por conversa. Um chat.send com um turno em andamento recebe error com code: "turn_in_progress"; o cliente espera o chat.end ou cancela.
  • Confirmação (ADR-010). O cliente não tem estado de confirmação: a Juniper pergunta ("Posso apagar esses três? É irreversível.") e o "sim" é só o próximo chat.send. O sistema interpreta a resposta (consent.py), nunca o cliente.
  • Mensagem fora de ordem não existe: os chat.token de um turno chegam em ordem e antes do chat.end desse turno.
  • Cancelar para a geração no próximo ponto de controle. As ações que já executaram continuam no histórico (o estado precisa ser verdadeiro); o texto parcial que ainda não virou resposta é descartado [a confirmar o detalhe na T-076].

6. Sessões

Uma conexão fica ligada a uma conversa por vez.

DireçãoTipoCamposEfeito
cliente → servidorsession.newidAbre uma conversa nova (a atual fica salva).
cliente → servidorsession.resumeid, session_id ou latestRetoma uma conversa.
cliente → servidorsession.listid, limit?Lista as conversas (mais recentes primeiro).
servidor → clientesession.statereply_to, session_id, turns, history?, noteEstado depois de new/resume. history traz o texto das mensagens para o cliente redesenhar a tela.
servidor → clientesession.listedreply_to, sessions[]Resposta de session.list: id, updated_at, turns, preview.
servidor → clientesession.detachedsession_id, reasonOutra conexão assumiu esta conversa.
  • O servidor usa o SessionStore (ADR-011; MongoDB em produção). O cliente não grava conversa nenhuma.
  • Mais de um cliente na mesma conversa: uma conversa só fica ligada a uma conexão por vez. Retomar uma conversa que está ligada a outra conexão a toma dela e avisa a antiga com session.detached. O usuário é um só, então o conflito é raro, e evita duas telas disputando o mesmo histórico [a confirmar]. Conversas diferentes em conexões diferentes funcionam à vontade.
  • Confirmação pendente não sobrevive a uma queda ou a um session.resume: depois de retomar, nada é executado sem um novo "sim" (regra do ADR-006 e do ADR-011).
  • history em session.state traz só role e text das mensagens visíveis (sem mensagens de tool).

7. Comandos de memória

Os comandos juniper memory ... passam pelo mesmo canal, como pedido e resposta.

{ "type": "memory.request", "id": "m-1", "op": "search", "args": { "query": "framework php", "limit": 5, "threshold": 0.8 } }
{ "type": "memory.result", "reply_to": "m-1", "ok": true,
  "data": { "results": [ { "id": "mem_20261014033000a1b2c3", "text": "O projeto X usa Laravel 11.", "type": "project", "score": 0.86 } ] } }
opargsdata
listtype?, all?memories[] com id, text, type, status, created_at.
searchquery, limit?, threshold?results[] (com score).
forgetiddeleted: ids apagados (a confirmação "Pode apagar?" é feita pelo cliente antes de enviar).
exportvectors?profile e memories[].
profile.get—profile (ou null).
profile.settext, name?, birth_date?, nationality?profile novo.
profile.forget—deleted: true.

memory reindex é administrativo e local ao servidor: não existe como op.

8. Erros

Falha de pedido: {"type":"error","reply_to":"...","code":"...","message":"...","retryable":true}. message é o texto amigável em PT-BR (o mesmo que o CLI mostra hoje com friendly_error); code é para o programa decidir.

codeQuandoretryable
unauthorizedToken ausente ou inválido.não
unsupported_versionprotocol_version incompatível.não
bad_requestMensagem malformada, tipo desconhecido, campo obrigatório ausente.não
turn_in_progresschat.send com um turno em andamento.sim (depois do chat.end)
session_not_foundsession.resume de um id que não existe.não
llm_authNenhum LLM aceitou as credenciais (LLMAuthError).não
llm_rate_limitLimite de requisições (LLMRateLimitError).sim
llm_unavailableTodos os providers fora do ar (LLMUnavailableError).sim
llm_timeoutDemorou demais (LLMTimeoutError).sim
llm_errorOutra falha de LLM (LLMError).não
memory_unavailableMongoDB fora do ar (MemoryUnavailableError).sim
not_foundId de memória inexistente.não
executor_unavailableA tool pedida roda num dispositivo que não está conectado (ADR-014).sim
internalFalha inesperada do servidor (o detalhe vai ao log, nunca ao cliente).sim

Os erros do LLM seguem a hierarquia de brain/llm/errors.py. Um erro de turno (llm_*) também fecha o turno com chat.end e finish: "error". A conexão continua aberta depois de qualquer erro de pedido.

Códigos de fechamento (faixa 4000–4999, de aplicação): 4400 protocolo violado, 4401 não autorizado, 4408 sem sinal de vida (heartbeat), 4409 substituída por outra conexão do mesmo dispositivo, 4426 versão incompatível. Do padrão do WebSocket: 1001 o servidor está saindo, 1012 o servidor está reiniciando (usado nos deploys).

9. Executor

O protocolo brain ↔ executor do ADR-007 passa a viajar na mesma conexão do cliente, com os mesmos nomes. Os detalhes de segurança, roteamento e a política da primeira tool (open_url) estão no ADR-014.

DireçãoTipoCampos
cliente → servidorregistertools[] (nome, descrição, parameters, tier)
servidor → clienteregisteredtools[] aceitas
servidor → clienteinvokecall_id, tool_name, arguments, timeout_ms
cliente → servidorresultcall_id, success, output?, error?, metadata?
{ "type": "invoke", "call_id": "k-9", "tool_name": "open_url", "arguments": { "url": "https://www.youtube.com" }, "timeout_ms": 10000 }
{ "type": "result", "call_id": "k-9", "success": true, "output": "Abri https://www.youtube.com no navegador." }
  • O register vem depois do welcome, só de clientes que são executores. O catálogo some do cérebro quando a conexão cai ou o heartbeat expira.
  • O servidor não escala tier: só envia invoke de tools com o tier que o cliente declarou (ADR-007).
  • Dois clientes sem catálogo (só chat) não interferem entre si.

10. Reconexão e retomada

O cliente reconecta sozinho quando a conexão cai.

  • Backoff exponencial com jitter: 1 s, 2 s, 4 s, 8 s, 16 s, depois 30 s fixos, com ±20% de variação. Zera depois de uma conexão estável por 30 s.
  • Fechamento 1012 (deploy): reconecta quase na hora (0 a 2 s de jitter).
  • Falhas que não adiantam repetir (4401, 4426): o cliente para e mostra o motivo.
  • Ao reconectar, o cliente manda hello com resume.session_id da conversa que estava aberta e, se for executor, repete o register.
  • Enquanto está offline, o cliente não enfileira mensagens: mostra "Juniper indisponível no momento" (ADR-007) e deixa o texto digitado na caixa para o usuário reenviar.

11. Fim de turno com o cliente caído

O cérebro não depende do cliente para terminar o trabalho.

  • Se a conexão cai no meio de um turno, o turno termina no servidor (limitado por agent.max_iterations e por um tempo total do turno, 120 s [a confirmar]), a conversa é salva com a resposta, e os chat.token que ninguém pôde ler são descartados. Ao retomar, session.state.history traz a resposta completa.
  • Como a confirmação é uma conversa (ADR-010), nenhum turno fica esperando alguém clicar: não há bloqueio a destravar.
  • A extração de memória em segundo plano (ADR-011, BackgroundExtractor) pertence à conversa, não à conexão: ela conclui os turnos já entregues mesmo que o cliente tenha saído.
  • Cancelamento explícito (chat.cancel) é diferente de queda: veja a seção 5.

12. Evolução do protocolo

  • protocol_version só muda em quebra de compatibilidade. Campos opcionais e tipos novos entram sem mudar a versão.
  • O contrato em código (T-074) é a fonte da verdade: modelos pydantic em brain/clients/protocol.py geram um JSON Schema versionado, e dele saem os tipos TypeScript do Electron (ADR-015). Este ADR descreve a intenção; em caso de divergência, vale o schema gerado.

Consequências

Positivas

  • Um canal só para chat, memória e executor: uma conexão para autenticar, reconectar e monitorar.
  • O cliente é realmente fino: sem estado de confirmação, sem armazenamento de conversa, sem lógica de agente.
  • O servidor continua autoridade do que aconteceu: uma queda do cliente não perde resposta nem memória.
  • O mesmo contrato serve o CLI remoto (Python) e o Electron (TypeScript).

Negativas

  • Estado no servidor por conexão (conversa ligada, executor registrado): precisa de limpeza correta quando a conexão cai.
  • Sem fila offline: se o cliente está sem rede, a mensagem não vai. É simples e honesto, mas menos "mágico" que um app de mensagens.
  • Turnos órfãos custam tokens: um turno terminado para ninguém ler ainda gasta LLM.
  • Reconexão e retomada são complexidade de engenharia que HTTP simples evitaria (mas o executor precisa de empurrar mensagens do servidor, então WebSocket seria necessário de qualquer forma).

Alternativas consideradas

  1. HTTP + SSE para o chat e WebSocket só para o executor. Funciona, mas são dois mecanismos de conexão, de autenticação e de reconexão. Descartada pela simplicidade de um canal só.
  2. gRPC. Streaming e tipos fortes, mas exige ferramentas e geração de código nos dois lados e não roda no navegador sem proxy. Excessivo para um usuário.
  3. JSON-RPC 2.0 puro. Padronizado, mas o chat é majoritariamente eventos em stream (um pedido, muitas respostas), que o JSON-RPC não modela bem. O envelope próprio é mais simples.
  4. Heartbeat só com os quadros ping/pong do WebSocket. Não é visível em todos os clientes (o renderer do Electron, o navegador) e alguns proxies ignoram. O heartbeat de aplicação é igual em todo lugar.
  5. Fila offline de mensagens no cliente. Adiada: exige ids de deduplicação e ordem garantida; o ganho não paga a complexidade para um usuário só.
  6. Conversa compartilhada entre conexões (transmitir os tokens para todos). Adiada: útil para vários dispositivos assistindo a mesma conversa, mas hoje não há esse caso.

Adendo (Sprint 3, T-086): extensões compatíveis

Não mudam protocol_version (campos e tipos novos são ignorados por quem não os conhece):

  • tools.request / tools.listed: lista as tools do servidor e dos executores conectados (juniper tools no modo server).
  • hello.trace e a mensagem trace (layer, text, at): o diário message.log; desligado por padrão (trace.enabled).
  • invoke.tier: o tier que o executor declarou no register (ADR-014).
  • A retomada (hello.resume, session.resume) exige exatamente um de session_id ou latest: true.
  • Uma confirmação pendente é descartada também quando outra conexão assume a conversa ou ela é retomada de novo.

Adendo (Sprint 4, T-148): mensagens de voz

Extensão compatível, sem mudar protocol_version (ADR-023): voice.start, voice.ready, voice.audio (nos dois sentidos, base64 de PCM 16 bits mono em quadro de texto, o que mantém a regra de recusar quadros binários), voice.state, voice.transcript, voice.say, voice.fallback, voice.text, voice.interrupt e voice.end; erros voice_unavailable e voice_busy (não retentáveis); hello.client.kind documenta mobile. O schema gerado é a fonte da verdade.

Adendo (2026-10-29, T-167): comandos do servidor no texto do chat

Extensão compatível, sem mudar protocol_version nem o schema. Um chat.send cujo texto é /vazou [nota] não vira turno: o servidor guarda o relato de vazamento (Auditoria de vazamentos) e responde com a sequência normal chat.started, chat.token e chat.end (finish: ok), com um turn_id próprio. Esse "turno" não entra no histórico da conversa, não chega ao modelo nem à memória e não ocupa a conversa (vale mesmo com uma resposta em andamento); por isso um cliente que conta turnos para recuperar uma queda (o bot do Telegram, ADR-016) não deve contá-lo. O comando é do servidor, então todo cliente de texto o tem sem mudar: o texto do app Android funciona com a versão já instalada. A mesma extensão vale para a frase falada «isso vazou» (ADR-023), que o VoiceSession trata antes de virar texto de chat. Quando o chat é cancelado pelo usuário (chat.cancel, ou falar por cima na voz), a mensagem do usuário fica no histórico e na transcrição, sem a resposta parcial; falha, timeout e queda da conexão continuam desfazendo o turno inteiro.
