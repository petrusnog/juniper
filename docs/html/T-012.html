T-012 — OllamaProvider

Primeiro provider de verdade: implementa o contrato LLMProvider (T-011) falando com um servidor Ollama local pela API HTTP. Arquivo: brain/llm/ollama_provider.py.

1. O que ele faz

É o "motorista" que sabe a língua do Ollama. Recebe Messages no vocabulário da Juniper, traduz, faz a chamada e traduz a resposta de volta.

chat(messages, tools)vocabulário Juniper
→
_to_ollama()traduz as mensagens
→
POST /api/chathttpx, stream:false
→
LLMResponseMessage + TokenUsage

Se algo der errado no caminho, o erro de rede ou HTTP vira um LLM*Error tipado (seção 4).

2. Configuração e uso

Construtor

  • url: padrão settings.llm.ollama.url
  • model: padrão settings.llm.ollama.model
  • timeout: padrão settings.llm.ollama.timeout (120 s)
  • transport: só para testes (servidor falso)

Exemplo

p = OllamaProvider()
r = await p.chat([
  Message("user", "oi")
])
print(r.message.content)
await p.aclose()

Use aclose() ao terminar para fechar a conexão HTTP.

3. A tradução: Juniper → Ollama

O Ollama é parecido com o formato OpenAI, mas não igual. Por isso o provider tem sua própria conversão em vez de usar Message.to_openai().

CampoOpenAI (to_openai)Ollama (_to_ollama)
content vazionull""
arguments da toolstring JSONdict
id da chamadasempre presenteausente; geramos call_<12 hex> na resposta
resposta de tooltool_call_idtool_name
max_tokensmax_tokensoptions.num_predict
temperatureraizoptions.temperature

Pedido enviado

POST http://localhost:11434/api/chat
{
  "model": "llama3.1",
  "messages": [{"role": "user", "content": "oi"}],
  "stream": false,
  "options": {"temperature": 0.7, "num_predict": 50},
  "tools": [ ... ]            // só se houver ferramentas
}

Resposta lida

{
  "model": "llama3.1",
  "message": {"role": "assistant", "content": "", "tool_calls": [
      {"function": {"name": "open_app", "arguments": {"target": "firefox"}}}]},
  "done_reason": "stop",
  "prompt_eval_count": 10,     // → prompt_tokens
  "eval_count": 5              // → completion_tokens (total = soma)
}

Sem os campos de contagem, usage fica None. Um content vazio vira None.

4. Erros

O provider nunca deixa vazar exceção do httpx: tudo vira um tipo da T-011.

ConnectError / erro de redeOllama desligado, porta errada, conexão resetada.LLMUnavailableError
TimeoutExceptionPassou do timeout.LLMTimeoutError
HTTP 5xxServidor com problema.LLMUnavailableError
HTTP 4xxEx.: 404 modelo não encontrado. É erro de configuração, não de disponibilidade.LLMError
JSON inválido / sem message / tool sem nomeResposta fora do esperado.LLMError

5. health_check e stream

health_check()

GET /api/tags. Devolve True se respondeu 2xx. Qualquer falha de rede vira False, sem lançar exceção.

stream()

Ainda lança NotImplementedError. Existe só para o provider poder ser instanciado. A implementação vem na T-014.

6. Como testar

7. Limitações conhecidas

Sem streaming até a T-014: a resposta aparece inteira, depois da espera.

CPU, não GPU: no WSL o Ollama não enxerga a RX 590 (ollama ps mostra 100% CPU). O provider não controla isso; o tempo de resposta é maior, e o timeout de 120 s é a folga.

Contexto de 4096 tokens (padrão do Ollama): conversas longas serão cortadas. A persona sozinha já usa cerca de 800 tokens.

Qualidade do 8B: o llama3.1 segue persona e tool calling pior que o 70B da Groq; por isso é o fallback.

Texto inválido: o provider espera UTF-8 válido. Bytes quebrados vindos do terminal precisam ser tratados pelo cliente (já feito no REPL, a fazer na T-040).
